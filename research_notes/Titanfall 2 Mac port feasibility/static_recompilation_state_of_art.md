# State of the art in static recompilation of video games (as of 2026-10-08), with emphasis on 2024-2026 and on x86 / x86-64 Windows

*Method note.* Every fact below comes from a page I actually opened (GitHub READMEs, GitHub REST API fields, news/blog pages). The fetch tool returns a small-model summary of each page, so numbers are copied from those summaries and not re-read from raw HTML; GitHub API fields (created_at, stars, licence) are exact values. Where a claim came only from a search-result snippet I say so and treat it as unverified. Commentary (Hacker News, opinion pieces) is labelled. The line drawn throughout: (a) static recompilation = translate original machine code ahead of time into C/C++/LLVM IR and compile it; (b) matching decompilation = rebuild source that recompiles to the same bytes (e.g. the GoldenEye and Pokemon Emerald projects that surfaced in searches); (c) emulation/JIT = translate at run time (Xenia, RPCS3, Dolphin, Rosetta-style). Only (a) is covered.

---

## 1. N64: Recomp (N64Recomp / N64ModernRuntime / RT64 / Zelda64Recomp and successors)

### Takeaway
N64Recomp is the mature reference design: MIPS to C one-for-one, driven by symbol/relocation metadata plus per-game TOML, linked against a hand-written libultra replacement (N64ModernRuntime) and an HLE-microcode GPU renderer (RT64, which has a Metal backend). It started with a game that already had a full decompilation's worth of symbols; by Oct 2026 at least 15 N64 titles are listed as released in one catalogue, but I found no authoritative per-title effort figures.

### Cited Findings
- N64Recomp takes an N64 binary plus metadata (symbols, relocations), splits it into functions, and recompiles each into a C function; translation is literal, e.g. `addiu $r4,$r4,0x20` becomes `ctx->r4 = ADD32(ctx->r4, 0X20);`; output is C that builds with MSVC/GCC/Clang. — [N64Recomp README](https://github.com/N64Recomp/N64Recomp)
- Indirect jumps: a `jr` is turned into a switch-case "if it can tell" it is a jump-table use; function pointers go through `LOOKUP_FUNC` macros; statically linked and relocatable overlays are supported (relocatable ones use `RELOC_HI16`-style macros so addresses are fixed up at run time). Configuration is TOML (input/output paths, function stubs, skipped functions, instruction patches). — [N64Recomp README](https://github.com/N64Recomp/N64Recomp)
- Stated limitations: modern MIPS GCC optimisations can cause issues; RSP overlay recompilation not yet supported; no custom metadata format. Licence MIT. — [N64Recomp README](https://github.com/N64Recomp/N64Recomp)
- GitHub API: N64Recomp repo created 2022-11-16, last push 2026-05-27, 8,201 stars, 454 forks, MIT. (Creation date may precede the public reveal.) — [GitHub API](https://api.github.com/repos/N64Recomp/N64Recomp)
- N64ModernRuntime = two libraries: `ultramodern` (reimplements libultra: threads, controllers, audio, message queues, timers, RSP task handling, VI timing; project supplies I/O callbacks and a renderer, RT64 recommended) and `librecomp` (overlay handling, PI DMA/ROM reads, EEPROM/SRAM/Flashram saves). C++20, GPL-3.0, 178 stars / 107 commits when read. — [N64ModernRuntime](https://github.com/N64Recomp/N64ModernRuntime)
- RT64 does not emulate cycle-accurately: it uses HLE of RDP/RSP microcode with GPU compute shaders; backends D3D12, Vulkan and Metal; runs on Windows, Linux and Apple Silicon macOS; MIT. — [RT64 README](https://github.com/rt64/rt64)
- Zelda64Recomp (Majora's Mask) supports Windows, Linux (Steam Deck Flatpak) and macOS (Apple Silicon or 7th-gen Intel, macOS 13+); needs D3D12, Vulkan 1.2 or Metal; mod support via Thunderstore; GPL-3.0; repo created 2023-10-23, 7,354 stars, last push 2026-09-25. — [Zelda64Recomp README](https://github.com/Zelda64Recomp/Zelda64Recomp), [GitHub API](https://api.github.com/repos/Zelda64Recomp/Zelda64Recomp)
- Coverage dated 13 May 2024 says Wiseguy had a working Majora's Mask port "in just two days" with the tool; the tool needs the user's own ROM; automated recompilation "isn't flawless" and typically needs manual fixes (notably timing/performance issues from modern hardware speed); output is not human-readable so modding is harder than with a decompilation. Titles named then: Banjo-Kazooie, Rocket: Robot on Wheels, Superman 64, Majora's Mask. — [VGC, 13 May 2024](https://www.videogameschronicle.com/news/unofficial-pc-ports-of-n64-games-could-be-about-to-get-a-lot-easier)
- Catalogue of released N64 recomps (page text says 16; the table I saw lists 15): Banjo-Kazooie v1.01 (Jan 2026), Bomberman 64 v1.0.0 (Mar 2026), Bomberman Hero v0.7.1 (May 2026), Dinosaur Planet v0.3.0 (May 2026), Donkey Kong 64 v1.0.2 (Sep 2026), Dr. Mario 64 v1.0.0 (Dec 2025), Duke Nukem Zero Hour v0.0.3 (Nov 2025), Extreme-G v1.0.0 (Aug 2026), Harvest Moon 64 v1.2.1 (Jul 2026), Majora's Mask v1.2.2 (Aug 2025), Mario Kart 64 v0.9.2 (Feb 2026), Mystical Ninja Goemon v0.2.0-dev (Jan 2026), Quest 64 v0.1 (Jan 2026), Snowboard Kids 2 v1.05 (Jun 2026), Star Fox 64 v1.0.3 (Feb 2026). — [Read Only Memo list, Oct 2026](https://readonlymemo.com/decompilation-projects-and-n64-recompiled-list/)
- A second catalogue (123 static recompilations across 22 platforms, plus 125 decompilations) calls Majora's Mask "the recomp that started it all", and also lists Conker's Bad Fur Day and a playable Banjo-Kazooie with mod support. — [Recompendium](https://nio03.github.io/unricopie/en/)
- DK64 Rekongpiled 1.0 shipped 30 Aug 2026 on N64: Recompiled + RT64, with Windows, Linux (x86-64 and ARM64, Flatpak) and macOS (ARM64 support mentioned) builds; the article gives no function counts, team or timeline. — [HWBusters](https://hwbusters.com/news/dk64-rekongpiled-hits-1-0-running-donkey-kong-64-natively-on-pc-without-an-emulator/)
- Other N64 recomps seen only as search-result titles (not opened, unverified): Smash64R, Starfox64Recomp (README title says Windows/Linux/macOS), Pokemon Snap ports. — [smash64r search hit](https://github.com/zestydevy/smash64r), [Starfox64Recomp search hit](https://github.com/sonicdcer/Starfox64Recomp)

### Inferences
- The "two days" figure for Majora's Mask is a best case: the game's tooling/symbol inputs were unusually rich, and the runtime (libultra replacement, RT64) had to be written first. The marginal cost of a later N64 title appears to be weeks to months (releases cluster Nov 2025 to Sep 2026) but I found no source stating per-title effort.
- The architecture that scales is: literal per-function lifter + small ABI of macros + a reusable runtime + a reusable renderer. That separation is what let one lifter serve ~15 titles.
- Because the output is plain C and RT64 has Metal, N64 recomps are the proof that recompiled-C plus a Metal renderer works on Apple Silicon. That is a 64-bit host target but a 32-bit-ish, in-order, big-endian guest, so it says little about x86 guests.

### Gaps
- No authoritative count of shipped N64 recomps (catalogues disagree: 16 stated vs 15 rows) and no per-title time-to-playable beyond Wiseguy's two-day claim for Majora's Mask.
- Exact first public release date of Zelda64Recomp not confirmed from a page I opened (only the May 2024 coverage date and the repo creation date of 2023-10-23).

## 2. Xbox 360: XenonRecomp, XenosRecomp, UnleashedRecomp, ReXGlue and followers

### Takeaway
XenonRecomp (PowerPC to C++) plus XenosRecomp (Xenos shader to HLSL to DXIL/SPIR-V) produced Sonic Unleashed Recompiled (revealed March 2025) and spawned a family of followers, most now built on ReXGlue, a separate BSD-licensed SDK that grafts Xenia's kernel onto ahead-of-time generated C++. The lifter is deliberately simple and pattern-based, needs per-game TOML input, supports no exceptions, and the whole ecosystem targets x86-64 hosts; I found no ARM64 or macOS build of any 360 recomp.

### Cited Findings
- XenonRecomp: converts XEX (plus optional XEXP title-update patch) to C++; each recompiled PPC function takes the CPU-state struct and a base-address pointer; memory loads byte-swap from big-endian and stores swap back; vector ops reverse whole 16-byte vectors; all memory ops are `volatile`; FPU/VMX denormal handling lives in the context struct. — [XenonRecomp README](https://github.com/hedge-dev/XenonRecomp)
- Indirect calls: a runtime "perfect hash table" in which dereferencing a 64-bit slot at (original instruction address x 2) yields the recompiled function address. Jump tables: companion tool XenonAnalyse pattern-matches predictable compiler idioms and writes them to TOML so switch cases are generated; setjmp/longjmp are redirected to native implementations. — [XenonRecomp README](https://github.com/hedge-dev/XenonRecomp)
- Per-game TOML must supply: XEX/XEXP paths, the addresses of the 8 register save/restore helper functions, setjmp/longjmp addresses, optional explicit function boundaries, mid-asm hooks, and invalid-instruction skip patterns. — [XenonRecomp README](https://github.com/hedge-dev/XenonRecomp)
- Stated limitations of XenonRecomp: MMIO unimplemented (e.g. XMA audio decoding); "no exception support"; jump-table detection is game-specific with "no fully generic solution"; function-boundary analysis struggles with functions containing jump tables. Requires Clang 18+. MIT. — [XenonRecomp README](https://github.com/hedge-dev/XenonRecomp)
- XenonRecomp repo created 2024-09-07, last push 2025-08-04 (so upstream has been quiet for over a year), 6,506 stars, 435 forks, MIT. — [GitHub API](https://api.github.com/repos/hedge-dev/XenonRecomp)
- XenosRecomp: Xbox 360 shader binaries to HLSL, then to DXIL (D3D12) or SPIR-V (Vulkan); batch mode builds an XXH3-hashed shader cache emitted as C++; the README warns users are "expected to modify the recompiler" and not to expect it to work out of the box; gaps include dynamic register indexing, integer constants, memory export, point size, mini-vertex-fetch; tuned to Sonic Unleashed. MIT. — [XenosRecomp README](https://github.com/hedge-dev/XenosRecomp)
- UnleashedRecomp: Windows 10+, Linux (Steam Deck Flatpak); macOS "not currently supported" but contributions welcome; renderer is a custom D3D12/Vulkan 1.2 backend (bindless, shader specialisation) built on a graphics abstraction layer ("plume"); a hand-written Xbox 360 kernel translation layer; Japanese version unsupported; code modding not yet implemented; some stutter inherited from the original; GPL-3.0; repo created 2024-09-30, last push 2026-06-29, 5,130 stars. — [UnleashedRecomp README](https://github.com/hedge-dev/UnleashedRecomp), [GitHub API](https://api.github.com/repos/hedge-dev/UnleashedRecomp)
- XenonRecomp's README credits Unleashed Recompiled with a ~20 MB executable-size reduction and several-millisecond frame-time improvements from optimisation (no baseline or hardware stated). — [XenonRecomp README](https://github.com/hedge-dev/XenonRecomp)
- Timeline: Time Extension (6 Mar 2025) reported XenonRecomp as the enabling tool, noted it "currently supports x86 systems only" because of x86 intrinsics, and speculated about 500+ delisted titles; it gave no per-game effort or performance numbers. — [Time Extension, 6 Mar 2025](https://www.timeextension.com/news/2025/03/new-xbox-360-recompilation-tool-will-give-lost-classics-another-chance-to-shine)
- Search snippets (pages not opened, unverified): reveal on 1 March 2025 via a streamed playthrough; XenonRecomp "created by 17 programmers"; co-creators Skyth and Sajid. — [Time Extension via search](https://www.timeextension.com/news/2025/03/this-new-unofficial-pc-port-of-sonic-unleashed-could-be-the-best-version-of-the-game-yet)
- HN commentary (8 Mar 2025, labelled commentary): static recompilation described as "a JIT with C++ as the IR"; sits between emulation and native port; project "still directly emulates" the 360 kernel; one commenter said XenonRecomp is "super basic and only matches patterns specific to a single compiler rather than devising a CFG". — [HN item](https://news.ycombinator.com/item?id=43296221), [HN mirror](https://brianlovin.com/hn/43226052)
- ReXGlue SDK: "Xbox 360 Recompilation Runtime and Toolkit", repo created 2026-01-22, 996 stars, 155 forks, last push 2026-10-02; pipeline = analyse, codegen, build; TOML config; the user must manually specify function boundaries and handle indirect calls/jump tables; runtime kernel/memory/VFS derived from Xenia but with the JIT replaced by AOT; README warns it needs "advanced knowledge" and is "not an alternative to Xenia"; hosts listed: Windows amd64 and Linux amd64/ARM64 (macOS not mentioned); v0.3.x; LICENSE file is BSD-3-Clause (copyright Tom Clay, with portions from Xenia). — [ReXGlue README](https://github.com/rexglue/rexglue-sdk), [ReXGlue wiki](https://github.com/rexglue/rexglue-sdk/wiki), [LICENSE](https://raw.githubusercontent.com/rexglue/rexglue-sdk/main/LICENSE), [GitHub API](https://api.github.com/repos/rexglue/rexglue-sdk)
- ReXGlue's creator "Tom" started it after seeing Sonic Unleashed Recompiled in 2025, working with the Fable 2 community and Ryan Fisher; says static recompilation enables things "extremely difficult or outright impossible" under JIT; GPU emulation from Xenia currently limits speed-ups; pilot title Blue Dragon; other work-in-progress titles named: Lost Odyssey, Banjo-Kazooie: Nuts & Bolts, Ninja Gaiden 2, Halo 3 beta, Crackdown 2, Viva Pinata. — [Read Only Memo interview](https://readonlymemo.com/rexglue-xbox-360-recompilation-interview/), [Time Extension, Mar 2026](https://timeextension.com/news/2026/03/i-hold-my-work-to-a-strict-standard-the-driving-force-behind-xbox-360-recomp-tool-rexglue-speaks-out)
- re:Blue (Blue Dragon, released Aug 2026 per the interview, catalogue says v1.2.1 Sep 2026): team of three (Tom, rcold, InfernoZotza); first fully custom PC-native renderer among 360 recomps, functional "within a couple months" but polishing took far longer; debug menus found in the game code helped testing; extensive game-specific work (bloom/specular/gamma retuned, new shaders, modding tools). — [Read Only Memo, re:Blue](https://readonlymemo.com/reblue-recompilation-blue-dragon-technical-interview/), [catalogue](https://readonlymemo.com/decompilation-projects-and-n64-recompiled-list/)
- Released ReXGlue titles per one catalogue: Sonic Unleashed (listed, though it predates ReXGlue), Banjo-Kazooie: Nuts & Bolts (Apr 2026), Blue Dragon v1.2.1 (Sep 2026), Kameo v0.2.1 (Jun 2026), Viva Pinata v1.13.0 (Oct 2026), Lollipop Chainsaw (Apr 2026), Naughty Bear v1.5.1 (Sep 2026). In progress: Ace Combat 6, Armored Core For Answer. — [Read Only Memo list](https://readonlymemo.com/decompilation-projects-and-n64-recompiled-list/)
- Other 360 recomps seen in catalogues: Skate 3 (claimed ~165 fps on high-end hardware), Silent Hill: Downpour (stable v1.0, 60 fps unlock) — catalogue claims only, not verified against the projects. — [Recompendium](https://nio03.github.io/unricopie/en/)
- The Simpsons Game (360): "around 82,000 game functions" converted to x86-64; playable but unfinished; graphics still use Xenia-derived emulation incl. shader translation; known issues: late-appearing objects, audio crackle, performance drops. — [Generation Amiga, 20 Jul 2026](https://www.generationamiga.com/2026/07/20/the-simpsons-game-returns-with-a-new-windows-and-linux-recompilation-release/)
- Platform claim (search snippet only, unverified): "every Xbox 360 recompilation project, on both XenonRecomp and ReXGlue, targets x86 PC platforms" with no ARM builds. — [Held Games snippet](https://heldgames.com/guides/recompiled-games-android). Counter-datapoint: ReXGlue README lists Linux ARM64 as a supported host. — [ReXGlue README](https://github.com/rexglue/rexglue-sdk). A blog post titled "Building Sonic Unleashed Recompiled On ARM Linux" exists (26 Mar 2026) but returned HTTP 403 so its contents are unverified. — [Interfacing Linux](https://interfacinglinux.com/2026/03/26/sonic-unleashed-running-natively-on-arm-linux-is-wild/)

### Inferences
- XenonRecomp's design (one C++ function per PPC function, a hash-table for indirect calls, TOML for the hard cases) is the closest published template for a "C, plus hand-written runtime, plus separate shader recompiler" pipeline, but its function-discovery is idiom-matching for one compiler family (Xbox 360 MSVC), which transfers only partly to x86-64 MSVC.
- The runtime is where most of the work and most of the variance lives: Unleashed and re:Blue wrote custom renderers; The Simpsons Game still leans on Xenia-derived graphics and is rougher. Renderer quality, not the CPU lift, separates "boots" from "good".
- Performance vs emulation: authors say recompilation beats JIT but I found no controlled benchmark; Digital Foundry coverage did not surface in my searches.
- Upstream XenonRecomp is dormant (last push Aug 2025); active development moved to ReXGlue (pushed 2026-10-02).

### Gaps
- No verified function/line counts for Sonic Unleashed or Blue Dragon, and no source for how long each ground-up took beyond "months".
- Digital Foundry / Eurogamer / Ars Technica coverage not found via search; Phoronix/GamingOnLinux not checked.
- Whether any 360 recomp builds on arm64 (the 403'd Interfacing Linux post and the ReXGlue "Linux ARM64" line suggest yes in some form) is unconfirmed.

## 3. Original Xbox (32-bit x86): xboxrecomp and Burnout 3

### Takeaway
Both things you heard of exist: `sp00nznet/xboxrecomp` is a Python-driven x86-to-C toolkit for original-Xbox XBE files, and its flagship title is Burnout 3: Takedown, which the author declared "playable end to end" in release v0.13.0 on 2026-10-07, i.e. yesterday. It is self-reported, about 7 months old, 147 stars, no independent coverage found. It is the closest published precedent to x86 to C for a commercial game, but it targets a Windows x86-64 host.

### Cited Findings
- xboxrecomp: "toolkit for statically recompiling original Xbox games from retail XBE executables into native Windows programs"; author/maintainer is sp00nznet (Ned Heller per the GitHub profile); MIT for project code, LGPL-2.1+ for xemu-derived APU/NV2A parts. — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp), [sp00nznet profile](https://github.com/sp00nznet)
- GitHub API: repo created 2026-03-06, last push 2026-10-07, 147 stars, 36 forks, MIT. Releases: v0.9.0 2026-09-12, v0.10.0 2026-09-16, v0.11.0 2026-09-20, v0.12.0 2026-09-27, v0.13.0 2026-10-07 (Burnout 3 playable), v0.13.1 2026-10-07 ("Cut Short"). (One page summary wrongly printed these as 2024; the API timestamps are 2026.) — [GitHub API repo](https://api.github.com/repos/sp00nznet/xboxrecomp), [GitHub API releases](https://api.github.com/repos/sp00nznet/xboxrecomp/releases?per_page=30)
- Pipeline (7 stages): XBE parse, Capstone disassembly + CFG, function identification (CRT/RenderWare/D3D/game), ABI/calling-convention recovery, x86-to-C lift, runtime link, MSVC compile. Lifter and analysis are in Python; generated code and runtime in C. Ghidra/IDA optional for symbols. — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp)
- Lifter model: guest registers are thread-local globals; condition codes reconstructed from operands at branch sites, with "snapshots" at control-flow joins; covers integer, x87 (precision control, rounding), MMX, SSE/SSE2, CPUID, RDMSR/WRMSR, atomics. Fixes in v0.13.0 included PUSHAD/POPAD (previously TODO). — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp)
- Indirect calls ("the hardest 10%"): dispatch tables built from runtime observations, calls guarded against recorded targets, fall-back to full dispatch; the game supplies `recomp_lookup(xbox_va)` (auto-generated) and `recomp_lookup_manual(xbox_va)` (hand-written overrides); vtable dispatch needed fixes and manual overrides during bring-up. Jump tables: arms decoded from code flow, and in v0.13.1 "lifted inside functions instead of dispatched". — [xboxrecomp README (raw)](https://raw.githubusercontent.com/sp00nznet/xboxrecomp/main/README.md), [README](https://github.com/sp00nznet/xboxrecomp)
- SEH: `__SEH_prolog`/`__SEH_epilog` patterns detected per title and bridged to Win32. Self-modifying code: listed as a known gap ("limited support"). — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp)
- Runtime libraries: kernel (170 of 371 ordinals routed), D3D8-to-D3D11, DirectSound, an MCPX APU and NV2A pushbuffer/rasterizer taken from xemu, XInput. Memory model reproduces the Xbox address space on Windows with `CreateFileMapping` and 28 mirror views. — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp)
- Burnout 3: 22,097 functions lifted into 367K lines of C; README says roughly two weeks from empty repo to "boots and renders 3D tracks"; v0.13.0 "playable end to end", single- and two-player. Other titles: Xbox Dashboard (boots through init), Wreckless (3,407 functions, boots to gameplay crash), Blood Wake (4,608 functions, scaffolded). — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp), [README (raw)](https://raw.githubusercontent.com/sp00nznet/xboxrecomp/main/README.md)
- Testing claims: 641 conformance tests / 5,843 vectors with zero mismatches, differential fuzzing of lifted C against real CPU execution. — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp)
- Host platforms: builds with MSVC and MinGW-w64; Linux/GCC runtime build added in v0.13.0; macOS/Docker used for conformance tests; ARM64 mentioned only as theoretical portability of the C. — [README (raw)](https://raw.githubusercontent.com/sp00nznet/xboxrecomp/main/README.md)
- Credits Claude Code explicitly in the README (see section 6). 40+ named contributors in the changelog. — [xboxrecomp README](https://github.com/sp00nznet/xboxrecomp)
- At least ten GitHub forks carry the same name and description (search hit list), e.g. [Heromachine/xboxrecomp](https://github.com/Heromachine/xboxrecomp), which indicates attention but also means there are copies to be careful about attributing.

### Inferences
- Repo creation (2026-03-06) to "playable" (2026-10-07) is about 7 months for the reference title, and the README's "two weeks to first 3D render" implies most of that went into correctness (flags at joins, x87, indirect calls, NV2A). Treat "two weeks" as time to first pixels, not to a game.
- The Burnout 3 claim is one day old and unverified by anyone I could find; treat it as promising, not established.
- Original-Xbox code is a far easier x86 case than Titanfall 2: 32-bit, a fixed kernel/ABI, one GPU with a known register interface, a few hundred thousand lines of C versus tens of millions.

### Gaps
- No independent coverage (press, video, third-party reproduction) of Burnout 3 running on xboxrecomp.
- No frame-rate or performance data; no statement of how much hand-written override code (`recomp_lookup_manual`) Burnout 3 needed.
- Other original-Xbox recompilation efforts besides this repo's forks: none found.

## 4. PS2 / PS3 / GameCube / Wii / Switch / other

### Takeaway
PS2Recomp (a generic tool) is explicitly experimental with weak GPU/VU performance; the Ace Combat 5 PS2 recomp (separate, Python lifter) is described as fully playable. Mario Kart Wii (Wiicompiled) is the first Wii recomp and already builds for Apple Silicon. PS3 recomp is runtime-library-heavy and honest that only two small titles reach gameplay, on Windows only. Suyu's "recompiler mode" is a different thing: CPU code only, still on an emulator's HLE layer, and the project was archived.

### Cited Findings
- PS2Recomp (ran-j): translates PS2 ELF (R5900) to C++; modules ps2xAnalyzer (ELF scan to TOML), ps2xRecomp, ps2xRuntime (memory, dispatch, syscalls), ps2xIOP; supports 128-bit MMI and VU0 macro mode; literal `ctx->r4 = ADD32(...)` style (same lineage as N64Recomp); README admits "performance is very bad for VU and GS" and "hardware emulation is partial and many paths are stubbed"; GPL-3.0; 3,340 stars, created 2025-04-12, last push 2026-10-05. — [PS2Recomp README](https://github.com/ran-j/PS2Recomp), [GitHub API](https://api.github.com/repos/ran-j/PS2Recomp)
- Ace Combat 5 (PS2, NTSC-U) by sal063: a Python tool translates every function to C, GCC compiles it together with a runtime standing in for the console; native Vulkan rendering instead of emulating the GS; relies on IDA Pro exports for function boundaries; 10,742 functions in 43 files; 3-5 minute build on 12 threads; "fully playable" on Windows; Apache 2.0; no AI mention. — [Ace Combat 5 README](https://github.com/sal063/Ace-Combat-5-Static-recompilation)
- Wiicompiled (Mario Kart Wii, PAL RMCP01 only): custom static recompiler for the PowerPC Broadway (DOL + REL), graphics layer "aurora" (GameCube/Wii compatibility layer; D3D, Vulkan, OpenGL); builds for Windows x64, Linux x64/ARM64, macOS 12+ on Apple Silicon and Intel; ~5 GB after one-time local compilation; physics checked against real hardware via ghost replays; "everything should be playable" but compatibility/rendering/networking still in flux; GPL-3.0; AI coding tools used. — [Wiicompiled README](https://github.com/patchzyy/wiicompiled)
- Public beta in August 2026 and an announcement on 15 Jul 2026 appear only in search snippets (not opened, unverified). — [Igor's Lab (snippet)](https://www.igorslab.de/en/mario-kart-wii-static-recompiled-pc-public-beta-august/)
- ps3recomp (sp00nznet and contributors, MIT): Python lift pipeline for PPU (incl. VMX), separate lifting of SPU programs (local store as arrays, DMA as memcpy, channels as message queues, per-image function-table dispatch), ~97 HLE modules taken from RPCS3 as reference; honest status table: only two titles reach gameplay (The Simpsons Arcade Game, Tornado Outbreak), Windows only; on macOS the Metal backend renders but there is no PPU boot scaffold ("will keep saying 'no' until a title actually boots"); v0.5.0 April 2026 to v0.13.0 October 2026; no AI credit. — [ps3recomp README](https://github.com/sp00nznet/ps3recomp)
- Suyu "recompiler mode" (Switch AArch64 to native x86-64): AOT translation of game CPU code only; graphics, audio and system services still run through the emulator's HLE; v0.04 declared final, repo archived 13 Sep 2026; no benchmarks or workflow documented. Secondary source only; another outlet's snippet says output is C then a .exe/ELF/Mach-O (conflict, unresolved). — [Held Games on Suyu](https://heldgames.com/guides/suyu-recompiler-switch-x86)
- Catalogue snippets: PS1 recomps (Crash Bandicoot 2, Ape Escape, Gran Turismo 2), SNES (Donkey Kong Country, F-Zero), PSXRecomp outputting WebAssembly — catalogue-level claims, projects not opened. — [Recompendium](https://nio03.github.io/unricopie/en/), [Held Games guide](https://heldgames.com/guides/retro-decompilation-recompilation-explained)

### Inferences

## 5. Has anyone statically recompiled a Windows PC game (32-bit or 64-bit x86) to another architecture or OS? (MOST IMPORTANT)

### Takeaway
Yes for 32-bit x86, in 2026, at scale of claims, and mostly by one prolific author with fast-moving, mostly unreviewed repos. Windows PE32 to native C is real: Mario Kart Arcade GP DX (a Windows arcade game) is reported fully playable; System Shock 2 (NewDark) and Lula/WET.EXE are lifted and running on a portable host on Linux/macOS; M-HT's SR (older, per-game) outputs ARM/ARM64/x64 for DOS/Windows games. For 64-bit Windows PE32+ the evidence is thin: one UE3 arcade game lifted with zero lift errors (attract mode reportedly renders, on Windows), and a 0-star fork targeting Linux via Wine DLLs that has lifted 311 functions of a utility. I found no verified x86-64 Windows game running on arm64 or macOS, and no recomp of a large commercial MSVC C++ D3D11 title like Titanfall 2.

### Cited Findings
- pcrecomp (sp00nznet; repo created 2026-02-27, 45 stars, last push 2026-10-08; README says MIT, GitHub licence detection says NOASSERTION): "unified toolbox" with x86-16/32/64 lifters, PE/NE/Mach-O parsers, C++ recovery (RTTI, vtables, demangling), DRM unpackers (SafeDisc, SteamStub, LZEXE), a 32-bit global-register runtime and a 64-bit explicit-CPU-struct runtime; differential testing against Unicorn (32-bit) or the host CPU (64-bit); claims 60+ projects; my read of its table: 46 listed, ~15 "playable/runs", ~20 lifted but not playable, ~11 planning. 64-bit lifter models 16 GPRs + 16 XMM, zero-extends 32-bit writes, rebuilds RIP-relative operands, handles indirect jumps by labelling every instruction in the function and ending in a local dispatch switch. No ARM64 target mentioned. — [pcrecomp README](https://github.com/sp00nznet/pcrecomp), [README (raw)](https://raw.githubusercontent.com/sp00nznet/pcrecomp/main/README.md), [GitHub API](https://api.github.com/repos/sp00nznet/pcrecomp)
- Same README: "Lifting a binary produces a derivative work of that binary, so the output carries whatever licence the original does." — [pcrecomp README](https://github.com/sp00nznet/pcrecomp)
- systemes3recomp (Namco System ES3 arcade games = commodity x86 PCs running Windows, VS2010 binaries): Mario Kart Arcade GP DX: 495/495 imports, 25,757 functions recovered, 29,645 lifted to C across 75 translation units, ~2.1M lines of generated C, 99.97% instruction coverage, "fully playable" (race completed, gamepad steering) at 1360x768 via real Direct3D; function discovery ~90% (28,597 found incl. 2,526 false positives). - Same repo: Star Wars: Battle Pods (x64, 609 imports) "renders its attract mode" through the same toolkit; MachStorm boots through CRT init. The pcrecomp README gives Battle Pods as "a shipping UE3 build": 3.6M instructions, 92,552 functions, 0 lift errors. (One summary of the first README says x64 titles are "handled separately" and the toolkit "requires 32-bit Windows": ambiguity about what host runs the x64 build is unresolved.) — [systemes3recomp README](https://github.com/sp00nznet/systemes3recomp), [README (raw)](https://github.com/sp00nznet/systemes3recomp/blob/main/README.md), [pcrecomp README (raw)](https://raw.githubusercontent.com/sp00nznet/pcrecomp/main/README.md)
- Rise of Nations: Rise of Legends (2006, MSVC 7.1 C++, Direct3D 9 loaded dynamically; sp00nznet): legends.exe is 15.5 MB; .text 13.25 MB; 19.2M instructions; 64,608 functions lifted (72,246 discovered by the legacy pass); 25,513 functions reachable only through data pointers (vtables; RTTI only in CRT/iostreams so vtables recovered by scanning data); 22.5M lines of C in 162 chunks; 99.53% recall / 69.9% precision of function discovery against IDA Pro 9.1; lifting took ~25 min, disassembly 50 min; the full build fails under parallel compilation for memory reasons; imports bind (429/429) and the lifted CRT runs headless, but D3D is not implemented and the game is not playable. Docs updated through 2026-10-02. — [rol README](https://github.com/sp00nznet/rol)
- Heavy Metal: FAKK2 (2000, Quake-3-derived): 13,660 functions across three binaries (fakk2.exe 4,118; gamex86.dll 8,303; cgamex86.dll 1,239), ~1.2M lines of C; image mapped at original virtual addresses; 194 Win32 imports forwarded to real DLLs, stdcall arg counts taken from SDK import libraries; engine init running (1,039 of 4,118 functions executed), renderer not implemented, not playable. — [heavymetal README](https://github.com/sp00nznet/heavymetal)
- NewDarkRecompiled (System Shock 2, NewDark 2.48; Owloeb; repo created 2026-10-03, 0 stars, MIT tools): lifter `lift.py` emits one C function per x86 function (~21,000 functions); registers in a struct, arithmetic flags as C locals the compiler can eliminate, x87 as `double`; guest memory flat (`host = M + guest`); two hosts: Windows (maps at 0x400000, redirects imports to real APIs) and a "portable host" (implements Windows API, C runtime, D3D9/DirectSound/DirectInput on SDL2 with OpenGL 2.1/ES 2.0; Ubuntu/Debian). Differential testing of every function/encoding against x86 emulation. Self-modifying code in the software renderer handled by mapping each write to exact instruction fields. Limitations: C++ exceptions in recompiled code unsupported (setjmp/longjmp work but skip destructors); SSE disabled (x87 fallback); shaders and cube/volume textures missing in portable host. - Lula / WET.EXE (1997 Windows PE32 game; Tombonator3000): Python recompiler (`cfg.py` CFG discovery using jump tables and relocation-derived pointers; `lift.py`; `flags.py` inter-procedural EFLAGS liveness), C99 output, indirect calls via relocation analysis plus manual hints in `config.json`, ret addresses enabling continuation-style returns; Win32/DirectDraw/DirectSound emulation, SDL2 platform layer, 4 GiB guest address space, single-threaded under a global lock; reaches the main menu headless on Linux/macOS, audio bit-exact, 5 end-to-end tests; gameplay/saving not verified. - linuxrecomp (BenderFendor; a fork of pcrecomp; repo created 2026-09-18, 0 stars, 0 forks, no licence detected): PE32+/AMD64 to native Linux, Win32 API taken from Wine's own DLLs via winelib rather than reimplemented; maps Win64 to System V calling convention; 32-bit runtime has an explicit `recomp32_cpu` struct. - M-HT/SR (older, long-running, 322 commits, 421 stars): static recompiler for DOS and Windows x86 game executables; takes the exe plus per-game information, emits x86 / ARM / LLVM IR (llasm) / x64 assembler; hosts Windows x86/x64, Linux x86/x64/ARM/ARM64/RISC-V64, macOS x64/ARM64; games: Albion, X-COM UFO Defense, X-COM Terror from the Deep, Warcraft Orcs & Humans, Septerra Core, Battle Isle 3; MIT with GPL/LGPL-compatible options. — [M-HT/SR](https://github.com/M-HT/SR)
- sp00nznet's profile lists 285 repos, including recomps of KOTOR (PC), Civilization III: Conquests (Steam), Blake Stone, Hover!, Virtual Springfield, Encarta 97, NeXTDoom, Microsoft Bob. — [sp00nznet profile](https://github.com/sp00nznet?tab=repositories)
- Another sp00nznet title from search hits (not opened): `gta` (GTA 1997 / London / GTA 2 for Windows x86-64), `saintsrow` (Saints Row 360), `psprecomp`, `systemes3recomp` — evidence of breadth. — [search hit: gta](https://github.com/sp00nznet/gta)
- Press and catalogue coverage of 2026 recomp activity (PC Gamer headline, Read Only Memo, Recompendium, Held Games) focuses on consoles; the Held Games explainer states it has no mentions of x86 PC game recompilation. — [Held Games guide](https://heldgames.com/guides/retro-decompilation-recompilation-explained), [PC Gamer (headline only; body truncated)](https://www.pcgamer.com/gaming-industry/if-youre-not-paying-attention-to-retro-game-recompilations-youre-missing-the-most-exciting-thing-in-gaming-right-now/)

### Inferences
- Plain statement: as of 2026-10-08 I found no verified static recomp of a modern (2010s) 64-bit Windows D3D11 game to arm64 or macOS, and no 64-bit commercial PC game shown to be playable via a static recompiler. The closest: Battle Pods (x64 UE3, attract mode, Windows host, README-level claim), Rise of Legends (same toolchain family as Titanfall 2 and 13 MB of .text, but 32-bit, not yet running), and the linuxrecomp pipeline (64-bit, Linux, early).
- Almost all of these projects are 32-bit and keep the guest in a flat memory image at the original address (0x400000 style) with real Windows DLL imports. That model does not port directly to macOS; the portable variants (NewDark portable host, Lula) reimplement Win32 and use SDL2. Titanfall 2's 64-bit PE with a large 64-bit address space and many system DLLs would need the 64-bit "explicit CPU struct" path, which is the least mature.
- Scale comparison: Rise of Legends (13.25 MB .text, 19.2M instructions) produced 22.5M lines of C and could not be built in parallel on the author's machine. If Titanfall 2's "tens of MB" of code is 2x-5x that, 45M-110M lines of C would follow by rough extrapolation (my estimate, not a sourced figure); that implies chunked or per-module compilation and a lazy/hybrid strategy as linuxrecomp already assumes.
- The projects in this family were all created in 2026 (pcrecomp Feb 2026; xboxrecomp Mar 2026; linuxrecomp Sep 2026; NewDark Oct 2026). They are weeks to months old, mostly single-author, and their "playable" claims are self-reported.

### Gaps
- No project found that runs a 64-bit Windows game on arm64 or macOS; no x86-64 to arm64 lifter found at all (the C output is portable in principle, but I found no one who has done it for a 64-bit PC game).
- Battle Pods: contradictory descriptions (attract mode renders; "handled separately"); what host and what runtime it uses is unclear; not independently verified.
- Whether Rise of Legends, KOTOR, Civ III or other sp00nznet titles ever progressed beyond bring-up: not checked project by project.
- Searches for Hacker News/Hackaday/Phoronix commentary on x86 PC recomps in 2025-2026 returned nothing specific.

## 7. Common failure modes and limitations the authors describe

### Takeaway
Across every project the same five problems recur: function boundaries and code/data discrimination need external input (symbols, IDA/Ghidra exports, hand TOML); indirect control flow (jump tables, vtables, function pointers) is solved per game with pattern matching, runtime logging and manual overrides; exceptions and setjmp-style unwinding are the weakest area; hardware/OS emulation (GPU, audio, kernel) dominates effort; and builds get very large.

### Cited Findings
- Needing symbols/boundaries: N64Recomp requires symbol and relocation metadata input; ReXGlue says you "will spend significant time manually specifying function boundaries, providing missing kernel imports, and iterating on codegen output"; XenonRecomp wants explicit function boundaries in TOML for problem cases; Ace Combat 5 uses IDA Pro exports; Rise of Legends' discovery had 99.53% recall but 69.9% precision against IDA (8,058 "invented" functions in the legacy pass); systemes3recomp's discovery was ~90% accurate with 2,526 false positives, and an extent-clamping bug had overcounted code ~20x because of shared epilogues. — [N64Recomp](https://github.com/N64Recomp/N64Recomp), [ReXGlue README](https://github.com/rexglue/rexglue-sdk), [XenonRecomp](https://github.com/hedge-dev/XenonRecomp), [Ace Combat 5](https://github.com/sal063/Ace-Combat-5-Static-recompilation), [rol](https://github.com/sp00nznet/rol), [systemes3recomp](https://github.com/sp00nznet/systemes3recomp)
- Jump tables / manual TOML: XenonRecomp's XenonAnalyse emits jump-table TOML and "no fully generic solution exists"; N64Recomp converts `jr` to a switch only "if it can tell"; ReXGlue docs call for manual handling of indirect calls and jump tables; xboxrecomp v0.13.1 fixed jump-table arms being dispatched instead of lifted inline. — [XenonRecomp](https://github.com/hedge-dev/XenonRecomp), [N64Recomp](https://github.com/N64Recomp/N64Recomp), [ReXGlue wiki](https://github.com/rexglue/rexglue-sdk/wiki), [xboxrecomp](https://github.com/sp00nznet/xboxrecomp)
- Function pointers / vtables: xboxrecomp calls ICALL "the hardest 10%", resolved via runtime-observed dispatch tables plus manual overrides; Rise of Legends has 25,513 functions reachable only through data pointers and no game-class RTTI, so vtables are recovered by data-section scanning; linuxrecomp lists adjustor thunks and COM boundaries as missing. — [xboxrecomp README (raw)](https://raw.githubusercontent.com/sp00nznet/xboxrecomp/main/README.md), [rol](https://github.com/sp00nznet/rol), [linuxrecomp ROADMAP](https://raw.githubusercontent.com/BenderFendor/linuxrecomp/main/docs/linux64/ROADMAP.md)
- Exceptions: XenonRecomp has "no exception support" (link register use, arbitrary handler jumps); NewDarkRecompiled does not support C++ exceptions inside recompiled code (setjmp/longjmp skip destructors); xboxrecomp detects SEH prologue patterns per title; linuxrecomp lists SEH, C++ exceptions and `.pdata/.xdata` handler bodies as not yet done. — [XenonRecomp](https://github.com/hedge-dev/XenonRecomp), [NewDark](https://github.com/Owloeb/NewDarkRecompiled), [xboxrecomp](https://github.com/sp00nznet/xboxrecomp), [linuxrecomp ROADMAP](https://raw.githubusercontent.com/BenderFendor/linuxrecomp/main/docs/linux64/ROADMAP.md)
- Self-modifying / runtime-generated code: xboxrecomp lists it as limited; NewDark handles one case (a software renderer's self-patching) by mapping each write to exact instruction fields; N64Recomp supports overlays/relocations but not RSP overlays. I did not find any project that handles a JIT or arbitrary runtime-generated code. — [xboxrecomp](https://github.com/sp00nznet/xboxrecomp), [NewDark](https://github.com/Owloeb/NewDarkRecompiled), [N64Recomp](https://github.com/N64Recomp/N64Recomp)
- SIMD: NewDark disables SSE paths and uses x87 fallbacks; XenonRecomp's output depends on x86 intrinsics (so hosts are x86 only per Time Extension); VMX vectors are fully byte-reversed. — [NewDark](https://github.com/Owloeb/NewDarkRecompiled), [Time Extension](https://www.timeextension.com/news/2025/03/new-xbox-360-recompilation-tool-will-give-lost-classics-another-chance-to-shine), [XenonRecomp](https://github.com/hedge-dev/XenonRecomp)
- Hand patches / timing: N64 recompiles typically need manual fixes for performance and timing at modern speeds (VGC); Unleashed still has glitches above 60 FPS and stutter inherited from the original; The Simpsons Game: animation bugs above 30 fps; re:Blue needed retuned bloom/specular/gamma and new shaders. — [VGC](https://www.videogameschronicle.com/news/unofficial-pc-ports-of-n64-games-could-be-about-to-get-a-lot-easier), [UnleashedRecomp](https://github.com/hedge-dev/UnleashedRecomp), [Generation Amiga](https://www.generationamiga.com/2026/07/20/the-simpsons-game-returns-with-a-new-windows-and-linux-recompilation-release/), [Read Only Memo, re:Blue](https://readonlymemo.com/reblue-recompilation-blue-dragon-technical-interview/)
- Per-title shader/GPU work: XenosRecomp tells users to expect to modify it; PS2Recomp admits poor GS/VU performance; xboxrecomp's NV2A path is partial. — [XenosRecomp](https://github.com/hedge-dev/XenosRecomp), [PS2Recomp](https://github.com/ran-j/PS2Recomp), [xboxrecomp](https://github.com/sp00nznet/xboxrecomp)
- Build scale: Rise of Legends' 22.5M lines in 162 chunks cannot be built in parallel on the author's machine (memory); Ace Combat 5 split into 43 files, 3-5 min; NewDark first build ~20 min then incremental patching. — [rol](https://github.com/sp00nznet/rol), [Ace Combat 5](https://github.com/sal063/Ace-Combat-5-Static-recompilation), [NewDark](https://github.com/Owloeb/NewDarkRecompiled)
- Middleware stays real or must be replaced: Rise of Legends keeps NovodeX PhysX, Bink and SpeedTree as real binaries; NewDark's cutscene decoder is limited to AVI/Indeo 5 without the original ffmpeg.dll. — [rol](https://github.com/sp00nznet/rol), [NewDark](https://github.com/Owloeb/NewDarkRecompiled)
- Honest status labelling is rare: ps3recomp keeps a table that says "no" for unproven platforms; most sp00nznet repos use phase tables (P0-P10) which makes "lifted" vs "running" visible. — [ps3recomp](https://github.com/sp00nznet/ps3recomp), [rol](https://github.com/sp00nznet/rol)

### Inferences
- For a 64-bit MSVC C++ D3D11 game the three hardest items are exactly the three the authors list as weakest: C++ exceptions/SEH (x64 uses table-based unwinding in `.pdata/.xdata`, not prologue patterns), vtable/data-pointer-only function reachability (Rise of Legends measured 25,513 such functions), and SIMD (x64 MSVC emits SSE2 by default, so the x87/SSE-disabled shortcut used in NewDark is unavailable).
- No project here has shown threading with real concurrency at scale (Lula runs under a global lock; xboxrecomp calls multi-threaded titles harder); Titanfall 2 is heavily multi-threaded (my knowledge, not sourced here).

### Gaps
- No source describing how any project handles the memory-ordering difference between x86 guest and arm64 host; none of the sources I opened discuss it.
- No source on handling of anti-tamper/DRM or on online-service dependency for a modern title (not relevant for SP-only, but unsourced).

## 8. Licences (can the main tools be reused in a personal project?)

- Derivative-work warning from pcrecomp: lifting a binary produces a derivative work, so the output carries the original's licence; N64/Xbox/Wii projects ship tools only, not game assets or pre-built game binaries, and require the user's own copy. — [pcrecomp README](https://github.com/sp00nznet/pcrecomp), [Held Games guide](https://heldgames.com/guides/retro-decompilation-recompilation-explained), [NewDark README](https://github.com/Owloeb/NewDarkRecompiled)

### Inferences
- A private, non-distributed Titanfall 2 Mac port can read and borrow from any of these. If any GPL code is merged into your runtime and you later share it, the whole combination must be GPL; MIT/BSD/Apache code (RT64, XenonRecomp, N64Recomp, ReXGlue) avoids that.
- Legal exposure is about distributing the generated C or built binaries (game-derived), not about using the tools; this is not legal advice.

### Gaps
- I did not independently confirm the Zelda64Recomp AI-contribution ban from the licence text itself (only from a page summary).
- Licence of Plume (UnleashedRecomp's graphics abstraction layer) not checked.

## 9. Host-platform evidence relevant to arm64 macOS (derived question)

### Takeaway
Recompiled-C output has already been shipped on Apple Silicon for N64 (Zelda64Recomp, DK64 Rekongpiled, via RT64/Metal) and for Wii (Wiicompiled); PS3Recomp has a Metal renderer but cannot boot a game on macOS; the 360 recomps are x86-only in practice; and no x86 or x86-64 source recomp has been shown on arm64 macOS except old per-game work by M-HT (SR).

### Cited Findings
- RT64 provides a Metal backend; Zelda64Recomp supports Apple Silicon macOS 13+. — [RT64](https://github.com/rt64/rt64), [Zelda64Recomp](https://github.com/Zelda64Recomp/Zelda64Recomp)
- Wiicompiled: macOS 12+ on Apple Silicon and Intel (x86_64-v3). — [Wiicompiled](https://github.com/patchzyy/wiicompiled)
- ps3recomp: Metal backend renders but no PPU boot on macOS. — [ps3recomp](https://github.com/sp00nznet/ps3recomp)
- UnleashedRecomp: macOS unsupported. ReXGlue: Windows amd64 and Linux amd64/ARM64 listed. XenonRecomp: x86 only (Time Extension, 2025). — [UnleashedRecomp](https://github.com/hedge-dev/UnleashedRecomp), [ReXGlue](https://github.com/rexglue/rexglue-sdk), [Time Extension](https://www.timeextension.com/news/2025/03/new-xbox-360-recompilation-tool-will-give-lost-classics-another-chance-to-shine)
- M-HT/SR emits ARM and macOS ARM64 for x86 DOS/Windows exes (per-game). — [M-HT/SR](https://github.com/M-HT/SR)
- xboxrecomp: macOS used for Docker-based conformance tests, ARM64 only theoretical. — [xboxrecomp README (raw)](https://raw.githubusercontent.com/sp00nznet/xboxrecomp/main/README.md)

### Inferences
- A Direct3D 11 to Metal shim (or DXBC/DXIL to MSL) is not yet demonstrated by any recomp project I found; ps3recomp (Metal, partial) and RT64 (Metal) are the nearest renderer precedents.

### Gaps
- No project reported on x86 flag/memory-model costs when targeting arm64, or on x86 TSO vs arm64 weak ordering.
