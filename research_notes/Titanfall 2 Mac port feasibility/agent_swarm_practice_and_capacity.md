## 1. Case studies of large agent-run engineering projects

### Takeaway
The best-documented runs are Carlini's Claude C compiler (16 parallel Opus 4.6 agents, ~2,000 sessions, ~$20k, 100k lines Rust) and Cursor's planner/worker experiments (hundreds of agents, ~1M-line browser in about a week). All had a fast, trusted oracle (test suites, GCC, byte-identical output). The decompilation and port-style cases (Snowboard Kids 2, Ladybird LibJS) are much smaller in agent count and were human-steered. I found no published case of an agent swarm statically recompiling a large Windows game.

### Cited Findings

#### A. Anthropic C compiler (Nicholas Carlini, Safeguards team, published 2026-02-05)
- Model: Opus 4.6. Team: "16 agents" on one shared codebase over "nearly 2,000 Claude Code sessions" across "two weeks". — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Cost/tokens: "2 billion input tokens" and "140 million output tokens"; "total cost just under $20,000". — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Result: ~100,000-line Rust C compiler; "99% pass rate" on most compiler test suites incl. GCC torture tests; builds Linux 6.9 on x86, ARM and RISC-V, and also QEMU, FFmpeg, SQLite, Postgres, Redis. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Correctness: high-quality test suites; GCC used "as an online known-good compiler oracle"; a CI pipeline to prevent regressions. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Harness: an infinite bash loop starts a fresh Claude Code session in a Docker container; the shared repo is mounted as upstream; each agent clones to a local workspace, then pulls, merges and pushes. Agents claim tasks by writing a lock file in `current_tasks/`; git sync forces a second claimant to pick another task; Claude resolves merge conflicts itself; no explicit orchestrator ("Claude picks up the next most obvious problem"). Each session starts "with no context", so agents maintain extensive READMEs and progress files. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Oracle design tips from the author: keep test output small to avoid context pollution (log details to files, one-line "ERROR [reason]" format, pre-compute summary stats); counter "time blindness" with a `--fast` flag running a deterministic 1-10% random sample per agent; when all 16 agents hit the same Linux-kernel bug, he built a GCC-vs-Claude random file-split test so agents could bisect and debug different failures in parallel. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Specialised side agents: one deduplicated code, one worked on compiler performance, one on generated-code efficiency, one gave Rust-design critique, one kept docs. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Author's stated limitations: no 16-bit x86 code generator (output exceeded the 32 KB real-mode limit, so it calls GCC); no own assembler or linker; generated code "not very efficient"; "New features and bugfixes frequently broke existing functionality"; he "tried (hard!)" to fix the gaps without full success; autonomous work makes it "easy to see tests pass and assume the job is done" and he is uneasy about unverified deployed code. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Model history: Opus 4.5 was "the first to cross a threshold" for a functional compiler passing large suites but could not compile large real projects; earlier Opus 4 models were "barely capable". — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Outside critique (secondary press): output is not a drop-in replacement; Rust quality "reasonable" but below expert level; commenters argue the $20k excludes the training-data contribution. — [The Register, 2026-02-09](https://www.theregister.com/2026/02/09/claude_opus_46_compiler/)

#### B. Cursor long-running multi-agent experiments
- "Scaling long-running autonomous coding" (2026-01-14): models GPT-5.2, GPT-5.1-Codex and Opus 4.5; "hundreds of concurrent agents", "trillions of tokens", runs up to 3+ weeks. A web browser took ~1 week (1M+ lines, ~1,000 files). Page also lists other runs: Solid-to-React migration (3+ weeks, +266K/-193K edits), video rendering (25x speed-up), Java LSP (7.4K commits, 550K LoC), Windows 7 emulator (14.6K commits, 1.2M LoC), Excel (12K commits, 1.6M LoC); I did not verify whether the last three are described as working products. — [Cursor](https://cursor.com/blog/scaling-agents)
- Architecture evolution: (1) agents self-coordinating via a shared file with locks failed (locks held too long or never released; "Twenty agents would slow down to the effective throughput of two or three"); (2) optimistic concurrency made agents "risk-averse", avoiding hard tasks for small safe changes; (3) planners create tasks recursively, workers just execute, a judge decides whether to continue each cycle: "solved most of our coordination problems". — [Cursor](https://cursor.com/blog/scaling-agents)
- Model-role lessons: GPT-5.2 is a better planner than GPT-5.1-Codex even though the latter is coding-specialised; Opus 4.5 "tends to stop earlier and take shortcuts"; "the prompts matter more" than harness or model; removing an integrator role removed a bottleneck. — [Cursor](https://cursor.com/blog/scaling-agents)
- Stated limitations: agents "occasionally run for far too long", need periodic fresh starts against drift, coordination "nowhere near optimal". — [Cursor](https://cursor.com/blog/scaling-agents)
- Follow-up post (2026-02-05 as extracted): about 1,000 commits/hour at peak, ~10M tool calls over a week with hundreds of agents on one large Linux VM running a week unattended; requiring 100% correctness before every commit caused serialisation, so they accepted a "small but stable rate of errors"; "constraints are more effective than instructions" (e.g. "No TODOs"); concrete ranges ("generate 20-100 tasks") beat vague directives; disk I/O from concurrent compilation, not tokens, was the main infrastructure bottleneck. — [Cursor](https://cursor.com/blog/self-driving-codebases)
- Independent check (commentary): Simon Willison found the browser built and ran on macOS with obvious rendering glitches but legible pages; the initial release had failing CI and no build instructions (fixed within about a day); he does not expect such projects to rival Chrome/Firefox/WebKit soon. — [Simon Willison](https://simonwillison.net/2026/Jan/19/scaling-long-running-autonomous-coding/)
- No dollar cost for the Cursor runs was stated on the pages I read (only "trillions of tokens"). — [Cursor](https://cursor.com/blog/scaling-agents)

#### C. Decompilation, porting and migration
- Snowboard Kids 2 (N64) matching decompilation, Chris Lewis (2025-11-04): Claude and Codex run in parallel; oracle is compile with the original toolchain (GCC 2.7.2) and compare object code byte-for-byte via decomp.me, giving a 0-100% match score; per-function agent subdirectory with a CLAUDE.md. Strengths: pattern recognition, patience across variants. Weaknesses: struct field byte offsets, repeated C89 syntax errors, tangled control flow. Author: "a long way from vibe coding" for matching decompilation. — [Chris Lewis](https://blog.chrislewis.au/using-coding-agents-to-decompile-nintendo-64-games/)
- Same project, "one-shot decompilation" (Simon Willison write-up, 2025-12-06): Opus 4.5 driven by a bash script (`vacuum.sh`) that picks the simplest unmatched function by heuristic score and runs `claude -p "decompile the function ..."`. Match progress 20% to 25% (Sep 3 to Nov 17), then 25% to 45% (Nov 17 to Dec 2). Lewis notes a good match should also look like plausible period code, not just match bytes. Cost and failure rates not given. — [Simon Willison](https://simonwillison.net/2025/Dec/6/one-shot-decompilation/)
- Ladybird LibJS C++ to Rust (Andreas Kling, 2026-02-23): Claude Code and Codex; ~25,000 lines of Rust in about two weeks (estimated months by hand); "human-directed, not autonomous" via hundreds of small prompts; requirement of byte-for-byte identical output from both pipelines; verified with test262 (52,898 tests), 12,461 Ladybird regression tests, lockstep C++/Rust execution on live content, and benchmarks; zero regressions; multiple review passes with different models; code deliberately stays "translated from C++" rather than idiomatic. — [Ladybird](https://ladybird.org/posts/adopting-rust/)

#### D. Other multi-agent / long-horizon projects with numbers
- OpenAI "harness engineering" (Codex, five months, internal beta product), secondary summary only because openai.com returned 403: seven people, >1M lines, ~1 billion tokens/day (~$2-3k/day at market rates), 3-5 PRs per engineer per day rising to 5-10 after Codex 5.2, inner-loop build target of one minute, zero human pre-merge review (post-merge sampling), requirements encoded in repo docs; limitations: zero-to-one work needs significant human steering, refactors with unclear interfaces are hard. A search snippet gave different PR numbers (3 engineers growing to 7, ~1,500 PRs); treat as UNVERIFIED and possibly different time snapshots. — [ZenML summary of OpenAI write-up](https://zenml.io/llmops-database/extreme-harness-engineering-building-production-software-with-zero-human-written-code)
- Anthropic "Harness design for long-running application development" (Prithvi Rajasekaran, 2026-03-24): planner/generator/evaluator on Opus 4.5 then 4.6; one task cost $9 and 20 minutes solo vs $200 and 6 hours with the full harness; another ran 3h50m for $124.70; self-evaluation leniency and "context anxiety" were failure modes; as models improved, sprint decomposition could be dropped (>2 hours of coherent work) because "every component in a harness encodes an assumption about what the model can't do". — [Anthropic Engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Anthropic "Effective harnesses for long-running agents" (Justin Young, 2025-11-26): initializer agent + incremental coding agent; JSON feature list with every feature initially "failing"; `claude-progress.txt` plus git history; instruction that removing or editing tests is "unacceptable"; failure modes were declaring victory early, one-shotting, and untested features. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic multi-agent research system (date not shown on fetched text): orchestrator-worker with Opus 4 lead and Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on an internal research eval; agents use ~4x and multi-agent ~15x the tokens of chat; "most coding tasks involve fewer truly parallelizable tasks than research". — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- Carlini average per session is roughly 1M input and 70k output tokens, or about $10 (2B/140M/$20k divided by ~2,000 sessions). Per agent-day it is about $90. These are my arithmetic, not stated figures.
- Opus 4.6 predates the newer tokenizer that the pricing page says yields ~30% more tokens for the same text (4.7 and later), so the same project on current models would report more tokens.
- $20,000 is about 200 months of the Max 5x list price ($100/month). A Carlini-scale swarm is not something a $100 subscription replicates; only a small fraction of that throughput fits (see section 3).
- Wall-clock-to-result ratios in the cases that match a binary/oracle (Ladybird ~2 weeks per 25k lines, human-steered; Lewis ~20 points of match in 2 weeks, one agent loop) suggest oracle-gated, serial or lightly parallel work is what a single subscription can sustain.

### Gaps
- No published case of an agent swarm doing static recompilation of a large Windows game, or any large lifting/recompiler project, was found.
- Cursor dollar costs, and Cursor's per-role model assignments beyond the planner finding, were not on the pages read.
- Lewis's cost, subscription tier, session counts and failure rates were not given.
- Large C-to-Rust or TypeScript-to-Go/Rust migrations with agent counts and cost: only Ladybird found; nothing else verifiable.
- OpenAI primary page not opened (403); Hacker News threads were not retrieved.

## 2. Organisational patterns that worked, and reported failure modes

### Takeaway
Success tracked three things: a fast mechanical oracle that agents cannot weaken; decomposition into independently claimable units with simple coordination (lock files or planner-worker, not shared locks among peers); and persistent written state (progress files, feature lists, READMEs) because sessions start cold. Failures cluster around regressions, risk-averse or short-cutting agents, test gaming or premature "done", drift, and runaway runs.

### Cited Findings

#### Patterns
- Fast, strong oracle: Carlini says the verifier defines what Claude solves; GCC as oracle, test suites, CI; Ladybird demanded byte-identical output plus 52,898 test262 tests; Lewis's byte-match score. — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Ladybird](https://ladybird.org/posts/adopting-rust/), [Chris Lewis](https://blog.chrislewis.au/using-coding-agents-to-decompile-nintendo-64-games/)
- Decomposition and claiming: lock files in `current_tasks/` with git as arbiter (Carlini, 16 peers); planners generating tasks for workers with a judge each cycle (Cursor). Peer locking at larger scale failed for Cursor. — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Cursor](https://cursor.com/blog/scaling-agents)
- Progress log / persistent state: READMEs and progress files (Carlini); `claude-progress.txt` and a JSON feature list marked failing until verified (Anthropic harness post). — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Limiting context pollution: terse greppable oracle output, summary stats pre-computed, sampled `--fast` runs; delegating verbose operations to subagents; hooks that filter test output before the model sees it. — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Claude Code costs doc](https://code.claude.com/docs/en/costs)
- Merge handling: Carlini lets Claude resolve git merge conflicts; Claude Code agent teams warn that two teammates editing one file overwrite each other and advise partitioning files; worktrees isolate parallel sessions and subagents. — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Agent teams](https://code.claude.com/docs/en/agent-teams), [Run agents in parallel](https://code.claude.com/docs/en/agents)
- Regression gates: CI pipeline (Carlini); "unacceptable to remove or edit tests" instruction (Anthropic harness); Claude Code hooks (`TaskCompleted`, `TeammateIdle`) can block completion with exit code 2. Cursor chose not to require 100% correctness per commit because it serialised work, accepting a small stable error rate. — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Agent teams](https://code.claude.com/docs/en/agent-teams), [Cursor](https://cursor.com/blog/self-driving-codebases)
- Simplicity: Cursor reports many improvements "came from removing complexity". Anthropic found harness scaffolding could be removed as models improved. — [Cursor](https://cursor.com/blog/scaling-agents), [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Separate evaluator: self-evaluation is lenient, so a separate evaluator agent (Playwright-driven) was used; "worth the cost when the task sits beyond what the current model does reliably solo". — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Workers sorted by easiest first: Lewis's script picks the lowest-complexity unmatched function first (heuristic score). — [Simon Willison](https://simonwillison.net/2025/Dec/6/one-shot-decompilation/)
- Stronger vs cheaper models: Cursor found planner quality matters (GPT-5.2 over a coding-tuned model). Anthropic's research system used Opus lead with Sonnet subagents. Claude Code docs advise Sonnet for agent-team teammates, Haiku for simple subagent tasks, Opus for complex architecture/multi-step reasoning, and provide an `opusplan` alias (Opus in plan mode, Sonnet in execution). No source I found reports a swarm built on a small/cheap worker model; Carlini used Opus 4.6 throughout. — [Cursor](https://cursor.com/blog/scaling-agents), [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system), [Costs](https://code.claude.com/docs/en/costs), [Model config](https://code.claude.com/docs/en/model-config)

#### Failure modes reported
- Regressions: "New features and bugfixes frequently broke existing functionality" (Carlini). — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- Plateau on the hard tail: Carlini could not close 16-bit x86 or assembler/linker gaps despite trying; Lewis's agents struggled on tangled control flow and struct offsets. — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Chris Lewis](https://blog.chrislewis.au/using-coding-agents-to-decompile-nintendo-64-games/)
- Risk aversion and shortcuts: Cursor's optimistic-concurrency version made agents avoid hard tasks; Opus 4.5 "stops earlier and takes shortcuts when convenient". — [Cursor](https://cursor.com/blog/scaling-agents)
- Premature completion and test weakening risk: agents declared victory early or marked features done untested; hence the no-editing-tests instruction. — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Duplicated work / all agents on the same bug: Carlini's kernel failure where every agent chased one bug; Cursor's lock bottleneck. Research-system delegation needed explicit task boundaries to prevent duplicate effort. — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler), [Anthropic research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Runaway cost/time: Cursor agents "occasionally run for far too long"; Claude Code docs cap a dynamic workflow at 1,000 agents per run to bound runaway scripts and warn above 25 agents or ~1.5M projected tokens. — [Cursor](https://cursor.com/blog/scaling-agents), [Workflows](https://code.claude.com/docs/en/workflows)
- Drift: Cursor needed periodic fresh starts. — [Cursor](https://cursor.com/blog/scaling-agents)
- Spec fidelity: byte-match alone may produce implausible source (Lewis); Ladybird's output deliberately stays non-idiomatic. — [Simon Willison](https://simonwillison.net/2025/Dec/6/one-shot-decompilation/), [Ladybird](https://ladybird.org/posts/adopting-rust/)
- Context anxiety / early wrap-up near perceived context limit; reduced on Opus 4.6. — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Overhead for coding: Anthropic itself says multi-agent suits high-value, highly parallel tasks and coding has fewer parallelisable pieces than research; Claude Code docs say agent teams are poor for sequential or same-file work. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system), [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Explicit test-gaming (agents editing or special-casing tests) as an observed incident: I found only the preventive instruction, not a documented incident. See Gaps.

### Inferences
- For a recompilation project the closest analogues are Lewis (byte-match oracle, per-unit tasks, simplest-first ordering, `claude -p` loop) and Carlini (differential oracle against a known-good implementation, fast sampled test mode, per-agent fresh sessions). A differential or golden-output gate that is deterministic and sampled for speed is the recurring ingredient.
- The pattern "easy units first, hard tail stalls" appears in both Lewis and Carlini; budget the hard tail for human or strongest-model attention instead of assuming linear progress.
- Small cheap workers have no documented success at this scale; the evidence supports using a stronger model for planning/evaluation/hard units and Sonnet-class for bulk work, but that is Anthropic guidance, not measured results.

### Gaps
- No documented incident of agents deleting/weakening tests to pass in the sources read (only preventive instructions).
- Cursor's exact lock/merge conflict handling beyond what is summarised; Carlini's conflict-rate statistics not given.
- No quantitative comparison of cheap-worker vs strong-worker outcomes for coding.

## 3. Claude specifics (checked against Anthropic pages, 2026-10-08)

### Takeaway
Haiku 5.5 exists and is the newest small model (Haiku 4.5 is now legacy). Current line-up is Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5. Max 5x is $100/month, with a 5-hour session limit and an all-model weekly limit, and Fable is capped at up to 50% of the weekly limit before usage credits apply. Anthropic publishes no hours-per-week or tokens-per-week figures on the pages I opened, and no public per-task token figure supports a precise tasks-per-week estimate.

#### Orchestration features (Claude Code docs)
- Subagents: per-agent model (`model:` frontmatter alias or full ID, or per-invocation); precedence: per-invocation, then frontmatter, then `CLAUDE_CODE_SUBAGENT_MODEL`, then main model; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` pins all subagents (v2.1.257+); default 20 concurrent subagents (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`); nesting up to three layers; `isolation: worktree` (v2.1.203+); background by default. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Dynamic workflows: a JavaScript script Claude writes orchestrates "dozens to hundreds" of agents (`agent()`, `pipeline()`, `parallel()`); up to 16 concurrent agents by default (configurable 1-256), 1,000 agents per run, 4,096 items per pipeline; resumable within a session; per-agent model choice; counts toward plan limits; "Large workflow" warning above 25 agents or 1.5M projected tokens; pauses and auto-resumes on a usage limit only in an interactive subscription session, not in `claude -p`, background sessions or agent teams. Available on all paid plans. — [Workflows](https://code.claude.com/docs/en/workflows)
- Agent teams: experimental, off by default (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`); shared task list with file-locked claiming, mailbox messaging; no worktree isolation; no session resumption of in-process teammates; guidance 3-5 teammates, 5-6 tasks each; docs say ~7x tokens versus a standard session when teammates run in plan mode; recommend Sonnet teammates. — [Agent teams](https://code.claude.com/docs/en/agent-teams), [Costs](https://code.claude.com/docs/en/costs)
- Other: agent view (`claude agents`, research preview) for background sessions; `/batch` skill splits a change into 5-30 worktree-isolated subagents; Projects (public beta on Pro and Max) run parallel cloud threads; worktrees give each session its own checkout. — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- Subagent/workflow requests have a five-minute cache TTL by default even on a subscription; `subagentPromptCacheTtl: 1h` extends it (main conversation gets one hour on a subscription). — [Workflows](https://code.claude.com/docs/en/workflows)
- Headless: `claude -p` with `--output-format json` reports `total_cost_usd` (client-side estimate), `--allowedTools`, `--permission-mode`, and the Agent SDK in Python/TypeScript for programmatic control. — [Headless](https://code.claude.com/docs/en/headless)

### Inferences
- Relative API price ratios show how much cheaper the cheap tiers are: Haiku 5.5 input is 20x cheaper than Sonnet 5.5, 40x cheaper than Opus 5.5 and 100x cheaper than Fable 5.1 (output 20x, 40x, 100x on the same figures: $0.50 vs $10, $20, $50). Subscription-limit weighting per model is not published, so API ratios are only a guide; Anthropic's statement that Fable consumes limits faster than other models is the only official qualitative signal.
- Because the weekly pool is shared by orchestrator, subagents, workflows, cloud sessions and routines, spending "half the weekly allowance" means a cap on total agent-hours across all of those, with Fable and Opus orchestration drawing disproportionately. Keep the orchestrator off Fable unless needed (Fable is capped at 50% of the weekly limit anyway).
- To plan capacity empirically: run one representative worker task, read the `/usage` weekly-bar movement and the attribution split, then divide the target half-week budget by that per-task cost. Use `subagentPromptCacheTtl: 1h` if tasks reuse a big shared prefix. This approach is my suggestion, not an Anthropic recommendation.
- `claude -p` loops (Lewis-style) draw from the subscription now, but the paused credit plan and the stated direction for `--bare` to become the default (which needs an API key) mean this could change; the new monthly API credit ($100 for Max 5x) is a small adjunct, not a substitute for subscription limits.
- Using a worker fleet at the documented caps (16 workflow agents, 20 subagents) will likely hit the 5-hour session limit before concurrency limits matter; unattended workflows do not auto-pause in `claude -p`, so a limit hit fails agents there.
