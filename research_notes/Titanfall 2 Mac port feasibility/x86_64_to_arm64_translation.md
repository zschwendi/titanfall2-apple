## (1) Existing x86-64 lifters and static binary translators (including academic work)

### Takeaway
No tool I found today can take a large, multithreaded, SSE-heavy Windows PE x64 binary and emit a working arm64 Mach-O. The practical tools are either ELF-only, SSE-less, archived, "lift one function at a time" libraries, or research prototypes whose largest verified targets are small benchmark suites (SPECint 2006, Phoenix). The most reusable pieces are Remill (instruction semantics) and Rellume (performance-oriented lifter) as libraries, plus the Lasagne/Arancini memory-ordering mappings as a design reference.

### Cited Findings

**Practitioner tools**
- **llvm-mctoll (Microsoft)**: repository archived by its owner on Oct 2, 2026 (read-only; six days before this research). Input is **ELF only** (x86-64 and Arm32 Linux). README says SIMD (SSE, AVX, Neon) cannot be raised, suggesting compiling input with SSE disabled; Windows, macOS and C++ binaries are listed as not yet implemented. x86-64 support is described as more mature than Arm32. Licence file present (type not confirmed from the page). — [github.com/microsoft/llvm-mctoll](https://github.com/microsoft/llvm-mctoll)
- **rev.ng**: GPLv2 overall (QEMU-derived dependencies) with MIT on individual files; 8,324 commits on `develop`; described as an open-source binary analysis framework on LLVM and QEMU with a decompiler. — [github.com/revng/revng](https://github.com/revng/revng). Docs say it uses QEMU to lift machine code, imports DWARF, PDB and IDA databases, and its decompiler emits C intended to be valid and recompilable. — [docs.rev.ng/what-is-revng](https://docs.rev.ng/what-is-revng/). I could **not** confirm PE/COFF x64 executable support, SSE handling, or any "translate to another ISA and run" capability from the pages I opened; the docs only claim recompilable C from the decompiler.
- **Remill (Trail of Bits)**: Apache-2.0; 1,159 commits on master; lifts x86/amd64 (stated to include AVX and AVX512), AArch64, SPARC32/64; primary platform Linux (Ubuntu 22.04), macOS supported, Windows listed as experimental (needs clang-cl). Positioned as a library for other tools (McSema, Anvill), not an end-to-end recompiler. — [github.com/lifting-bits/remill](https://github.com/lifting-bits/remill)
- **McSema**: archived by owner Aug 23, 2022 (read-only). Handled ELF and PE, 32/64-bit, "most integer, x87, MMX, SSE, and AVX operations"; built on Remill and requires Anvill. — [github.com/lifting-bits/mcsema](https://github.com/lifting-bits/mcsema)
- **Anvill**: AGPL-3.0; 558 commits; main branch consumes protobuf specs from a Ghidra plugin that the README says is currently closed source (older branch targets Binary Ninja); uses Remill for semantics. No stated PE x64 or scale figures. — [github.com/lifting-bits/anvill](https://github.com/lifting-bits/anvill)
- **Rellume (TU Munich)**: LGPLv2.1+; lifts x86-64, AArch64 and RISC-V64 to LLVM IR with the stated goal that lifted code runs as fast as the original; models SIMD so the optimiser can generate efficient code; 785 commits. README gives no Windows/PE or memory-model handling. — [github.com/aengelke/rellume](https://github.com/aengelke/rellume). Last push date of June 17, 2024 and Instrew's host/guest lists (guests x86-64 and RISC-V64; hosts x86-64 and AArch64; dynamic translator built on Rellume) **[UNVERIFIED: snippet]** — [search result](https://github.com/minhaozh/instrew/blob/master/README.md)
- **RetDec (Avast)**: "limited maintenance mode"; MIT; reads ELF, PE, Mach-O, COFF; supports x86-64 and AArch64; a decompiler to C, not a recompiler; PR-friendly but slow issue response. — [github.com/avast/retdec](https://github.com/avast/retdec)
- **Striga (May 2026)**: Python x86-64 to LLVM IR lifter; author says Remill was hard to compile; explicitly "not meant to be production-ready", no tests, only a small x86 subset, no SSE. Useful as a readable reference for flag modelling and "brightening" lifted code into functions. — [secret.club/2026/05/21/striga.html](https://secret.club/2026/05/21/striga.html)
- **Ghidra p-code lifters, angr, BinRec**: I did not open any primary page for these. See Gaps.

**Academic static / hybrid translators**
- **MirrorBall, "No Bit Left Behind" (UC Irvine, arXiv 2609.16423, 14 Sep 2026)**: fully static x86-64 to LLVM IR to AArch64 with no runtime translator; treats every byte offset as a possible instruction and builds a superset CFG, so no code/data heuristics; unresolvable indirect branches become dispatch-table lookups. Evaluated on **SPECint 2006 only** (12 programs, ELF, gcc 13.3.0). All 12 recompiled and ran correctly. Mean slowdown **3.74x** x86-64 to x86-64 round trip; **6.64x** mean for x86-64 to AArch64 over the nine benchmarks LLVM could compile as one module, **12.33x** when gcc, omnetpp and xalancbmk are included after splitting them into submodules (LLVM struggled with the huge code sections). Mean basic-block expansion **49.6x** (range 19.3x to 155.4x). Authors call it a deliberate negative result and say it is not the right choice for production today and is worse than mature dynamic translators for cross-ISA use. Prototype has **no multithreading, no C++ exception unwinding, no self-modifying code**; they cite Polynima (EuroSys 2024) as having handled threads. Registers modelled as thread-locals is named as the main overhead source. — [arXiv abs](https://arxiv.org/abs/2609.16423), [PDF text](https://arxiv.org/pdf/2609.16423)
- **Lasagne (PLDI 2022)**: static x86 to Arm translator with a formally proven concurrency mapping through its IR; preserves x86 ordering by inserting fences; optimisations that raise the abstraction of address computation cut fences by up to about 65% (average 45.5%). Authors from Edinburgh, TU Delft, TU Munich, St Andrews. — [PLDI'22 page](https://pldi22.sigplan.org/details/pldi-2022-pldi/52/Lasagne-A-Static-Binary-Translator-for-Weak-Memory-Model-Architectures). I could not open the paper, so its absolute overhead vs native is not recorded here.
- **Arancini (ASPLOS 2026)**: hybrid translator, best-effort static translation plus on-demand dynamic translation through a shared IR (ArancinIR); static side leaves unresolved indirect jumps as `br ptr` that the dynamic runtime resolves. Targets Arm and RISC-V. Evaluated on the **Phoenix multithreaded suite**, on ThunderX2 (56 cores) and SOPHON SG2042 (64 cores), against Lasagne ("improved mcToll") and Risotto. Slide results: Lasagne produced only partial or no translation for all seven Phoenix programs while Arancini completed all seven on Arm and RISC-V; Arancini is "up to 5x faster than dynamic translators" (16-thread runs). Formally verified mappings: plain store to `DMB ST; STR`, plain load to `LDR; DMB LD`, RMW to acquire-release RMW. — [authors' slide deck (TUM)](https://dse.in.tum.de/wp-content/uploads/2026/03/Arancini-Asplos26-unrolled.pdf). Venue/date/page numbers (ASPLOS '26, 22 Mar 2026, pp. 157-174) **[UNVERIFIED: snippet]** — [search result](https://www.st.ewi.tudelft.nl/sschakraborty/papers/ASPLOS2026-Arancini.pdf)
- **Risotto (ASPLOS 2023)**: dynamic (QEMU-based) translator with verified fence-placement; reported 6.7% average improvement over QEMU. — [TU Delft record](https://research.tudelft.nl/en/publications/risotto-a-dynamic-binary-translator-for-weak-memory-model-archite)
- **Polynima (EuroSys 2024, Deshpande, Parzefall, Hetzelt, Franz)**: "practical hybrid recompilation for multithreaded binaries"; abstract says no earlier recompiler adequately handled multithreaded programs. I could not get its evaluation numbers or benchmark list. — [OpenAlex abstract](https://api.openalex.org/works/doi:10.1145%2F3627703.3650065)

**Reference point from a different ISA pair (same technique, proven at game scale)**
- **XenonRecomp (Xbox 360 PPC to C++)** recompiled Sonic Unleashed (UnleashedRecomp). It takes function boundaries from the XEX `.pdata` for functions with stack frames and runs its own boundary analyser for the rest; jump tables are found by pattern (`mtctr r0`) and written to TOML for the user to confirm; virtual and indirect calls go through a runtime "perfect hash table" keyed on the original address. — [github.com/hedge-dev/XenonRecomp](https://github.com/hedge-dev/XenonRecomp)
- Other 2026 recomp projects with macOS arm64 builds (DK64 Rekongpiled v1.0.0, Aug 29 2026; Mario Kart Wii recomp, Jul 15 2026) are MIPS/PPC-to-C, not x86 **[UNVERIFIED: snippet]** — [hwbusters](https://hwbusters.com/news/dk64-rekongpiled-hits-1-0-running-donkey-kong-64-natively-on-pc-without-an-emulator/)

### Inferences
- Nothing in this list has been shown on a PE x64, multi-threaded, SSE-heavy, tens-of-MB-of-code target. The largest verified successes are SPECint 2006 (single-threaded ELF) and Phoenix (small, multithreaded). A Titanfall 2 recompiler would be new work built on parts, not a configuration of an existing tool.
- Best reusable parts, in order: (a) Remill semantics or Rellume as the instruction-to-IR layer (both handle SSE-class vectors; Rellume is optimiser-oriented); (b) the Lasagne/Arancini memory-ordering mappings as a spec; (c) XenonRecomp's pipeline shape (analyse `.pdata`, emit a config for jump tables, emit C/C++ or IR, runtime address-to-function table), which is the only proven game-scale static-recomp workflow I found.
- llvm-mctoll is now archived, ELF-only and SSE-less, so it is not a viable base; Lasagne's own pipeline depended on it, so reusing Lasagne means inheriting those limits.
- LLVM compile time and code-size scaling is a real risk: MirrorBall hit it on gcc-sized inputs even with a hand-picked ELF benchmark set. Tens of MB of Windows code needs module splitting and likely per-function lowering.

### Gaps
- BinRec, angr-based and Ghidra p-code-based lifters: no primary pages opened, so no status/licence/scale claims made.
- rev.ng PE/COFF x64 support and any rev.ng x86-64 to arm64 recompilation path: not confirmed.
- Lasagne and Polynima absolute performance numbers and benchmark lists (PDFs inaccessible).
- Any project that has statically recompiled a PE x64 game to arm64: I found none, but absence in search results is weak evidence.
- Rellume/Instrew last-commit dates and licence of Instrew: only from snippets.

## (2) Memory ordering: TSO vs weak memory, what Apple Silicon offers, and Rosetta's timeline

### Takeaway
I found **no supported API** for a native arm64 macOS process to switch its own threads into hardware TSO. The only known routes are (a) letting Rosetta/kernel do it for a translated x86_64 process, (b) an unsupported kext (TSOEnabler, needs SIP off, offsets for a Big Sur 11.2 beta), and (c) indirect VM-based routes (Rosetta-for-Linux VMs run the whole guest in TSO; Hypervisor.framework exposes `ACTLR_EL1` but I could not verify the TSO bit works there). Without hardware TSO, a static recompiler must pay for ordering in software, and this M3 Pro has LDAPR/STLR-class instructions (LRCPC and LRCPC2) to make that cheaper.

### Cited Findings

**Why TSO code breaks on ARM**
- The canonical message-passing case: thread 1 writes X then Y, thread 2 reads Y then asserts X; under x86-TSO the assert never fails, on ARMv8 it can. Translators must preserve guest ordering and this is hardest for strong-on-weak. — [Arancini slides](https://dse.in.tum.de/wp-content/uploads/2026/03/Arancini-Asplos26-unrolled.pdf)
- Apple's own porting guidance says the Intel Mac strong model adds implicit barriers while Apple silicon's weak model does not, so lock-free or custom synchronisation must be validated; recommends thread sanitizer. — [Apple: Addressing architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code.md)
- How often real programs are affected: I found no empirical frequency study. The Lasagne/Arancini/Risotto line treats it as a correctness requirement for any concurrent binary and the Asahi kernel thread describes hardware TSO as "basically non-negotiable" for x86 emulation (as summarised by the fetch tool; not verified verbatim). — [LKML cover letter thread](https://lists.infradead.org/pipermail/linux-arm-kernel/2024-May/926327.html). FEX's maintainers report that emulating TSO without hardware help is the largest single slowdown source and that it can crash complex apps (Unity games named). — [FEX-2306 release notes](https://newreleases.io/project/github/FEX-Emu/FEX/release/FEX-2306)

**What Apple Silicon provides and how Rosetta uses it**
- Apple silicon implements TSO as an implementation-defined bit in `ACTLR_EL1` (called `ACTLR.TSOEN` in one patch series); Asahi Linux exposes it per thread through `PR_{SET,GET}_MEM_MODEL` prctls; Asahi had shipped it downstream to thousands of users. — [LWN](https://lwn.net/Articles/969484/), [kernel patch thread](https://lkml.rescloud.iu.edu/2404.1/04768.html)
- Mainline Linux status: the arm64 maintainers objected (no architectural spec, cannot discover whether the context-switch instruction exists, ABI fragmentation concerns). I could only confirm the April-May 2024 state (not merged). — [infradead thread](https://lists.infradead.org/pipermail/linux-arm-kernel/2024-May/925581.html). Whether it was merged later: **[UNVERIFIED]**, I did not find a 2025-2026 source.
- Rosetta 2 relies on this hardware: M1 gives x86-style ordering for normal loads/stores, plus FlagM/FlagM2 and undocumented hardware support for x86 parity/adjust flags, and a non-standard FP mode matching x86 NaN and tininess behaviour. — [Dougall Johnson, "Why is Rosetta 2 fast?"](https://dougallj.wordpress.com/2022/11/09/why-is-rosetta-2-fast/)
- Normally the kernel enables TSO for translated processes by writing a special register on exit from the kernel; the TSOEnabler description says the same flag can be set per thread for arbitrary processes **[UNVERIFIED: snippet; the page summary I opened only confirmed the per-thread flag, not the "on kernel exit" detail]** — [TSOEnabler (gitee mirror)](https://gitee.com/guoami/TSOEnabler)

**Can a native arm64 macOS process enable TSO? (clear status)**
- **Supported way: none found.** Apple's "About the Rosetta translation environment" says translation applies to a whole process, arm64 and x86_64 cannot be mixed in one process, and Rosetta does not translate kernel extensions or VMs. The page has no mention of TSO or any opt-in. — [Apple docs](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment.md). The Apple Silicon documentation index lists no TSO/memory-model article. — [Apple Silicon docs index](https://developer.apple.com/documentation/apple-silicon.md)
- **Unsupported way: TSOEnabler kext.** Per its README: a kernel extension; exposes a `kern.tso_enable` sysctl after `kextload`; hard-coded memory offsets for macOS Big Sur 11.2 beta (20D5029f) so other builds need manual offset edits; SIP must be disabled unless you hold a KEXT signing certificate; all threads of an app must be enabled for it to work; pins affected threads to performance cores; install can need recovery mode. — [gitee mirror](https://gitee.com/guoami/TSOEnabler). Local probe: on macOS 27.0.1 `sysctl -a | grep -i tso` shows only network TSO entries (`net.inet.tcp.tso` etc.), so no `kern.tso_enable` exists in stock macOS 27. I did not test whether the kext could load on macOS 27 at all.
- **Indirect route 1, Virtualization.framework (Linux VM + Rosetta share):** macOS 13+ lets ARM Linux VMs run x86_64 Linux binaries via a Rosetta directory share (`VZLinuxRosettaDirectoryShare`); AOT-cache options from macOS 14; **in macOS 27 Intel translation for Linux apps is built into macOS and the install step is a no-op**. Apple's page does not mention TSO. — [Apple: Running Intel binaries in Linux VMs](https://developer.apple.com/tutorials/data/documentation/virtualization/running-intel-binaries-in-linux-vms.md). A third-party write-up says the whole VM runs in TSO mode once the Rosetta share is mapped, that Rosetta runs JIT-only there, and that without TSO "Rosetta explicitly does not provide those guarantees". — [threedots.ovh](https://threedots.ovh/blog/?p=447). I could not corroborate this with a primary source.
- **Indirect route 2, Hypervisor.framework:** the framework's `hv_sys_reg_t` list includes `HV_SYS_REG_ACTLR_EL1` (undocumented, no description), the framework requires the `com.apple.security.hypervisor` entitlement, and the framework index includes a per-VM IPA granule setting (`HV_IPA_GRANULE_4KB` / `16KB`). Whether a guest can actually set the TSO bit there is **[UNVERIFIED]**. — [Hypervisor](https://developer.apple.com/documentation/hypervisor.md), [hv_sys_reg_t](https://developer.apple.com/documentation/hypervisor/hv_sys_reg_t.md)
- **New in macOS 27, TSO relevance unknown:** an Apple Developer Forums thread (an Apple DTS engineer answering a Wine plus CPU-translator developer) says that to map memory below the 4 GB `__PAGEZERO` on arm64 you add the "Cross-architecture Compatibility Framework" capability in Xcode 27.0+ (adds entitlement `com.apple.developer.cross-architecture-support`, needs a provisioning profile) and link with a reduced `-pagezero_size`. The thread excerpt I read says nothing about TSO or 4K pages. I could not find Apple's documentation for the entitlement (the guessed doc URL 404'd). — [Apple forums thread 845976](https://developer.apple.com/forums/thread/845976)
- NixOS maintainers (May 2026) wrote that Wine will not run natively on aarch64-darwin until Apple changes macOS, possibly via an entitlement. — [NixOS Discourse](https://discourse.nixos.org/t/x86-64-darwin-removal-and-wine/77532)
- **What others do on macOS:** CodeWeavers ships a native-arm64 CrossOver preview (from Jul 31 / Aug 2026) that embeds a macOS port of FEX instead of Rosetta; requires macOS 26.5 or later; lacks D3DMetal, some launchers, and bottle migration at preview stage. How that FEX port handles memory ordering is **not documented in anything I could open**. — [macmagazine](https://macmagazine.com.br/post/2026/07/31/crossover-27-ganha-versao-de-teste-com-suporte-a-chips-apple-silicon/), [ithinkdiff](https://www.ithinkdiff.com/?p=343215), [borncity](https://borncity.com/news/crossover-fuer-mac-arm64-version-ohne-rosetta-2-verfuegbar/). The ithinkdiff piece says the preview targets CrossOver 28 while macmagazine and the NixOS thread call it CrossOver 27; sources conflict on version naming.
- Box64 does not target macOS (Linux on ARM64/RISC-V/LoongArch only). — [github.com/ptitSeb/box64](https://github.com/ptitSeb/box64). FEX upstream: the only macOS-linked FEX items I could open were a Podman community project running FEX inside a Linux microVM (libkrun, not Apple Virtualization Framework). — [Podman discussion 28549](https://github.com/containers/podman/discussions/28549). Upstream FEX issues requiring a 4K-page kernel, and Asahi's microVM workaround, are **[UNVERIFIED: snippet]**.
- Before the ARM64 builds, Wine on macOS Apple Silicon ran as x86_64-darwin builds under Rosetta 2 (NixOS thread, May 2026), and CrossOver 26.2.0 still depended on Rosetta 2 (ithinkdiff), so they inherit Rosetta's TSO. Game Porting Toolkit was not covered by any page I opened (I did not verify how it runs). — [NixOS thread](https://discourse.nixos.org/t/x86-64-darwin-removal-and-wine/77532), [ithinkdiff](https://www.ithinkdiff.com/?p=343215)

**Software alternatives when hardware TSO is unavailable**
- Full fence mapping (Lasagne/Arancini): plain store becomes `DMB ST; STR`, plain load becomes `LDR; DMB LD`, RMW becomes acquire-release RMW; formally verified as correct and minimal. — [Arancini slides](https://dse.in.tum.de/wp-content/uploads/2026/03/Arancini-Asplos26-unrolled.pdf). Lasagne's address-abstraction optimisation removes about 45.5% of fences on average (up to ~65%). — [PLDI'22 page](https://pldi22.sigplan.org/details/pldi-2022-pldi/52/Lasagne-A-Static-Binary-Translator-for-Weak-Memory-Model-Architectures). Risotto averaged 6.7% better than QEMU. — [TU Delft](https://research.tudelft.nl/en/publications/risotto-a-dynamic-binary-translator-for-weak-memory-model-archite)
- Acquire/release based emulation: FEX, when hardware TSO is missing, emulates the model with atomics and LRCPC instructions (and later LRCPC2 immediates). Its release notes say this is slow enough that disabling it is a common "performance fix". — [FEX-2306](https://newreleases.io/project/github/FEX-Emu/FEX/release/FEX-2306). Search snippets claiming "near 10x" cost came from other FEX release pages I did not open **[UNVERIFIED: snippet]** — [FEX-2308 listing](https://newreleases.io/project/github/FEX-Emu/FEX/release/FEX-2308)
- **Box64 `BOX64_DYNAREC_STRONGMEM`**: 0 = nothing special (default); 1 = some barriers when writing memory (limited TSO); 2 = level 1 plus barriers on SIMD instructions; 3 = level 2 plus more barriers "on a regular basis"; 4 = mimic QEMU-style TSO for evaluation. Higher levels = more correct, slower. — [Box64 USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)
- Hardware on the target: local probe on a test M3 Pro: `hw.optional.arm.FEAT_LRCPC = 1`, `FEAT_LRCPC2 = 1`, `FEAT_LSE = 1`, `FEAT_LSE2 = 1`, `FEAT_FlagM = 1`, `FEAT_FlagM2 = 1`, `FEAT_AFP = 1` on macOS 27.0.1.
- Microsoft's route for Windows on Arm: MSVC `/volatileMetadata` records which x64 memory accesses are volatile so an emulator can use acquire/release only there; without the metadata the emulator assumes every address is volatile. It was on by default in VS 2019 16.10 through VS 2022 and is off by default starting VS 2022 18.6; minimum VS 2019 16.10. — [Microsoft Learn](https://learn.microsoft.com/en-us/cpp/build/reference/volatile). A Hacker News commenter makes the same link for FEX. — [HN 45905850](https://hn.svelte.dev/item/45905850)
- "Run single-threaded": the only source I found is the Rosetta-in-VM write-up suggesting `taskset` pinning on Linux without TSO. — [threedots.ovh](https://threedots.ovh/blog/?p=447). No macOS equivalent verified.

**Rosetta phase-out timeline (Apple primary sources)**
- Apple support page: Rosetta is available for Apple silicon Macs on macOS 27 or earlier; starting with macOS 28, Rosetta functionality is available only for certain older, unmaintained games that rely on Intel-based frameworks. — [support.apple.com/102527](https://support.apple.com/en-us/102527)
- Apple developer docs (copyright 2026) repeat it: Rosetta is a general-purpose tool "through macOS 27", afterwards a subset for older unmaintained gaming titles that rely on Intel-based frameworks. Rosetta translates AVX and AVX2 but not AVX512. — [Apple docs](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment.md)
- Reported but not opened: macOS 28 expected late 2027; a beta-only `sudo game-test-tool enable` command for legacy-game testing. **[UNVERIFIED: snippet]** — [search result](https://www.techrepublic.com/article/news-apple-macos-26-4-rosetta-2-support-ending/). Local probe: `game-test-tool` is not present in `/usr/bin` on macOS 27.0.1; `/usr/libexec/rosetta` is present.

### Inferences
- For a static recompiler on macOS 27 the baseline assumption must be **no hardware TSO**. Plain loads and stores on shared data need either explicit ordering instructions or a proof that they are not shared.
- On ARMv8.3+ with RCpc, mapping every plain x86 load to LDAPR and every plain store to STLR gives the ordering x86-TSO requires (LDAPR/STLR allow store-then-load reordering, which TSO also allows). This is the mapping FEX uses when it lacks hardware TSO. M3 Pro reports FEAT_LRCPC and LRCPC2, so this is available. Cost is uncertain: I found no published number for LDAPR/STLR-everywhere on Apple cores.
- Lasagne-style fence elimination applies directly: stack accesses (`rsp`-relative), TLS, immutable data and provably thread-private memory need no ordering. For a job-system engine, most shared structures (queues, counters) are accessed with LOCK-prefixed instructions that map to acquire/release or seq-cst RMW anyway; the risky accesses are the plain publish-then-flag patterns, which is exactly what a "strongmem level 1-2" heuristic targets.
- `/volatileMetadata` would not help Titanfall 2 directly: the metadata only exists in binaries built with VS 2019 16.10 or later, and Titanfall 2 shipped in 2016 (inference from release date; the build toolchain is not verified).
- The new `com.apple.developer.cross-architecture-support` entitlement in Xcode 27 is the single most important lead for "what does macOS 27 give a translator". It is explicitly aimed at Wine plus CPU-translator runtimes. Concrete next steps that would resolve the TSO question: (a) read Apple's entitlement documentation / Xcode 27 capability help; (b) download the CrossOver ARM64 preview and inspect its entitlements with `codesign -d --entitlements -` and its FEX build for TSO use; (c) check the macOS 27 SDK headers for new thread or task flags. None of these were done.
- A pure-software static recompile that avoids Rosetta must be designed to be correct without TSO. The Rosetta-for-Linux-VM route could in principle supply TSO to native arm64 code in a guest, but a Linux guest has no Metal access, so it does not look viable for a graphical game (inference; not researched).
- Rosetta timeline: macOS 27 (the target) is the last release with full Rosetta, so "just run the Windows build under CrossOver/Rosetta" works through macOS 27. After that the surviving subset is described only for old games relying on Intel-based (macOS) frameworks, which a Wine-hosted Windows game may not match (inference; Apple has not said how eligibility is decided).

### Gaps
- No empirical study of how many real programs, or which patterns, break under ARM weak ordering was found.
- Absolute overhead numbers for fences, LDAPR/STLR-everywhere, or strongmem levels on Apple cores: not found (Lasagne/Arancini PDFs inaccessible; Arancini slides give only relative claims).
- Whether TSOEnabler can work on macOS 27 (SIP, signing, offsets): untested and no source after the Big Sur beta.
- Whether Hypervisor.framework guests can set the TSO bit; whether Virtualization.framework gives TSO to non-Rosetta processes in the guest: primary-source confirmation missing.
- Contents and TSO relevance of `com.apple.developer.cross-architecture-support`; how CrossOver's FEX port orders memory on macOS: CodeWeavers pages blocked.

## (3) Other classic static-translation obstacles

### Takeaway
Function discovery on Windows x64 is substantially easier than on ELF because `.pdata` gives a sorted table of function ranges and unwind data, and a proven game-recomp workflow (XenonRecomp) uses exactly that, but leaf functions are missing from the table, jump tables still need pattern recovery, and indirect calls need a runtime address-to-function map. SEH/C++ exception unwinding through recompiled code has no published solution I could find. SSE-to-NEON has mature libraries with documented edge-case differences. macOS 16K pages, no W+X, and the 4 GB `__PAGEZERO` need runtime shims.

### Cited Findings

**Function boundaries, tail calls, unwinding data**
- `.pdata` holds `RUNTIME_FUNCTION` entries (begin RVA, end RVA, unwind-info RVA), sorted, required for every function that allocates stack or calls another function. Leaf functions have no entry (the unwinder treats a missing entry as a leaf whose return address is at `[rsp]`). — [Microsoft: x64 exception handling](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64?view=msvc-170)
- `UNWIND_INFO` has flags for exception handler (`UNW_FLAG_EHANDLER`), termination handler (`UNW_FLAG_UHANDLER`) and chained info (`UNW_FLAG_CHAININFO`). The language-specific handler RVA and its data follow the unwind codes. Chained entries describe non-contiguous parts of one function (shrink-wrapping / split code), so one logical function can appear as several `RUNTIME_FUNCTION` ranges. Prolog size and unwind codes (`UWOP_PUSH_NONVOL`, `UWOP_ALLOC_*`, `UWOP_SET_FPREG`, `UWOP_SAVE_*`) describe the stack effect at each prolog offset. — same Microsoft page
- Dynamically generated code must register itself with `RtlAddFunctionTable` or `RtlInstallFunctionTableCallback`, otherwise exception handling and debugging are unreliable. — same Microsoft page
- Relocation table: no source opened on how much it helps; see Gaps.
- XenonRecomp (PPC, same idea): `.pdata` boundaries for frame-bearing functions plus a heuristic analyser, pattern-based jump-table detection emitted to a config file, runtime lookup table for virtual calls. — [XenonRecomp](https://github.com/hedge-dev/XenonRecomp)
- MirrorBall sidesteps discovery by lifting every byte offset (superset CFG) at about 49.6x block expansion and 3.74x slowdown; unresolved indirect branches go through a dispatch table. — [arXiv 2609.16423](https://arxiv.org/pdf/2609.16423)
- Arancini leaves unresolved indirect jumps to a dynamic translator at runtime. — [Arancini slides](https://dse.in.tum.de/wp-content/uploads/2026/03/Arancini-Asplos26-unrolled.pdf)
- Rosetta 2's indirect-branch handling: x86 CALL/RET become BL/RET with a shadow bookkeeping stack to keep return prediction; indirect branches use a compact two-level search over an x86-to-arm address map instead of a table entry per instruction. — [Dougall Johnson](https://dougallj.wordpress.com/2022/11/09/why-is-rosetta-2-fast/)

**Exceptions and the OS boundary**
- Arm64EC: x64 and Arm64EC code coexist in one process following x64 conventions (calling convention, stack use, struct layout); emulated x64 code runs under the built-in emulator; Arm64EC and plain Arm64 are mutually incompatible; most OS code loaded by an x64 app on Windows 11 Arm is Arm64EC. The page I read does not describe unwinding, exit thunks or indirect-call handling. — [Microsoft Learn: Arm64EC](https://learn.microsoft.com/en-us/windows/arm/arm64ec)
- MirrorBall explicitly lacks C++ exception unwinding and notes prior recompilers also deferred it; says it needs regenerating unwind metadata for the lifted IR. — [arXiv 2609.16423](https://arxiv.org/pdf/2609.16423)
- No source I opened describes how FEX, Prism or any static recompiler unwinds through translated MSVC frames (`__CxxFrameHandler3/4`, funclets). See Gaps.

**Flags, FP and SIMD**
- x86 flags: Rosetta uses ARM FlagM/FlagM2 (`CFINV`, `RMIF`, `SETF8/16`) plus Apple's extra hardware for parity/adjust (NZCV bits 26 and 27 per the article). — [Dougall Johnson](https://dougallj.wordpress.com/2022/11/09/why-is-rosetta-2-fast/). Local probe: this M3 Pro reports FEAT_FlagM and FEAT_FlagM2 and FEAT_AFP. Whether the Apple-private parity/adjust support is usable from a native process is not documented anywhere I read.
- Box64 flag-handling options: `BOX64_DYNAREC_SAFEFLAGS` 0 (CALL/RET never need flags, fastest/riskiest), 1 (default balance), 2 (all CALL/RET need flags). x87/NaN/rounding options: `FASTNAN`, `FASTROUND` (default 1 = ignore edge-case rounding), `X87DOUBLE`. — [Box64 USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)
- Apple: on arm64 `(uint32_t)INFINITY` saturates to `0xffffffff` and `(int32_t)INFINITY` to `0x7fffffff`, whereas x86_64 gives 0 and the "indefinite" `0x80000000`; audit float-to-int. — [Apple architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code.md)
- Rosetta supports AVX and AVX2 but not AVX512 (check `hw.optional.avx512f`). — [Apple Rosetta docs](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment.md)
- **sse2neon**: MIT; actively maintained (1,603 commits); covers SSE, SSE2, SSE3, SSSE3, SSE4.1, SSE4.2 and AES, **not AVX**; documents NaN differences in min/max, `_mm_rsqrt_ps(0)` giving NaN instead of INF, opt-in `SSE2NEON_PRECISE_*` macros (min/max, sqrt, etc.), warnings about frequent rounding-mode changes, `SSE2NEON_UNDEFINED_ZERO` for denormal handling; some intrinsics need many instructions (`_mm_maddubs_epi16` about 22); explicitly supports macOS ARM64 (Apple Clang 12+); used by 50+ projects including Blender. — [github.com/DLTcollab/sse2neon](https://github.com/DLTcollab/sse2neon)
- **SIMDe**: MIT-style; SSE through SSE4.1 complete, SSE4.2 partial, AVX, AVX2 and many AVX-512 subsets; NEON implemented on x86; 3,411 commits; caveats on `fenv.h` rounding, AVX test intrinsics and flag outputs. — [github.com/simd-everywhere/simde](https://github.com/simd-everywhere/simde)
- Neither library publishes game-scale performance data in the pages I read, and both operate at the intrinsic (source) level, not on machine-code.

**Memory layout, page size, W^X**
- Apple: Apple silicon page size differs from Intel; fetch it from `vm_page_size` (local probe: `hw.pagesize` = 16384). — [Apple architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code.md)
- A secondhand forum post quotes that Rosetta runs the x86 userspace "in 4K mode" via heavy XNU rework (the CPU cannot mix page sizes within an address space). — [techboards.net post, June 2024](https://techboards.net/threads/3d-games-working-on-apple-gpu-on-linux-at-4k.3696/page-5). Secondhand; native processes do not get this.
- Hypervisor.framework lets a VM choose a 4 KB or 16 KB IPA granule. — [Hypervisor docs](https://developer.apple.com/documentation/hypervisor.md)
- Apple DTS: mapping below the 4 GB `__PAGEZERO` on arm64 needs the cross-architecture-support entitlement plus `-pagezero_size` (example uses 0x4000); the example target address was `0x7ffe0000`; helper executables need their own App ID and a bare executable must be wrapped as a daemon/app. — [Apple forums 845976](https://developer.apple.com/forums/thread/845976)
- Wine on Apple Silicon `VirtualAlloc`/`VirtualFree` churn fragmenting the reserve region into ever more Mach VM regions (Wine bug 59476) **[UNVERIFIED: snippet]** — [search result](https://list.winehq.org/hyperkitty/list/wine-bugs@list.winehq.org/thread/IVZ5MWU2Q6EQRTDMMTUPD3RBGQMNGS5M/)
- W^X and JIT: Apple silicon never allows a page to be writable and executable at once, for every app (on Intel only for hardened-runtime apps). `MAP_JIT` needs `com.apple.security.cs.allow-jit` only if the app adopts the Hardened Runtime; with it, one `MAP_JIT` region is allowed; `pthread_jit_write_with_callback_np` plus the `com.apple.security.cs.jit-write-allowlist` entitlement is the newer write path (after which `pthread_jit_write_protect_np` is unavailable on macOS); `sys_icache_invalidate` is required because I-cache is not coherent. — [Apple: Porting JIT compilers](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon.md)

**Self-modifying or generated code in Titanfall 2**
- MirrorBall states self-modifying / runtime-generated code is fundamentally incompatible with a fully static pipeline. — [arXiv 2609.16423](https://arxiv.org/pdf/2609.16423)
- Titanfall 2 embeds a Squirrel script VM (described as the binding layer between the Source-derived engine and scripts); the source does not say whether Squirrel is interpreted or JITs. — [Northstar blog](https://northstar.tf/blog/vanilla-unrestricted-server-script/)

### Inferences
- Plan function discovery as: (1) every `RUNTIME_FUNCTION` entry, merging chained fragments into one logical function; (2) leaf functions and thunks found by following direct call targets and scanning gaps between entries; (3) a conservative fallback for unresolved indirect targets (dispatch table or dynamic translator) as Arancini and MirrorBall do. This is the same shape XenonRecomp uses.
- Tail calls (a `jmp` to another function's entry) are distinguishable from intra-function jumps using the `.pdata` ranges; "no entry" thunks and `noreturn` functions (e.g. `abort`, `__fastfail` paths) need a manual or pattern list since the unwind table does not mark them. This is reasoning, not from a source.
- MSVC jump tables are normally relative-offset tables in `.rdata`/`.text`; XenonRecomp's workflow (heuristic detection, human-confirmable config) is the realistic model. Relocation tables help locate pointer-sized tables of absolute addresses (vtables) but x64 PE code uses RIP-relative addressing, so `.reloc` is sparse for code. This is general PE knowledge, not sourced here.
- Cost of address-to-function dispatch: XenonRecomp's perfect-hash design is a single dependent load; Rosetta uses a two-level search. For vtable-heavy C++ expect an extra indirection per virtual call; no measured figure found.
- SEH/C++ exceptions will need a design of their own: either keep recompiled functions at 1:1 stack frames with synthesised `.pdata`-equivalent metadata and implement a Windows-style dispatcher (what MirrorBall says is needed), or use a table-driven side mechanism. No published static-recompiler solution was found, so treat as open.
- Windows-specific runtime pieces the recompiled code will assume (TEB via `gs:[0x30]`, `rdtsc`, `cpuid`, `KUSER_SHARED_DATA` at `0x7FFE0000`, 64K allocation granularity with 4K protection, `VirtualAlloc` semantics) are outside what the sources I opened cover. The Apple forum thread's `0x7ffe0000` example suggests low fixed addresses matter for Windows runtimes. Likely approach: replace `gs:` accesses with a register-held TEB pointer at lift time, return fake `cpuid`, wrap `rdtsc` with `cntvct_el0`, and implement `VirtualAlloc` on top of Mach VM at 16K granularity with guard-page emulation. This is design reasoning, not a sourced finding.
- Because the Windows game would be recompiled to native arm64 and no longer run under Wine, the process can be a normal native arm64 app with no hardened-runtime requirement unless it also contains a JIT/dynamic fallback; that decision drives whether `allow-jit` or the allowlist entitlements are needed.

### Gaps
- Relocation-table coverage and `.pdata` completeness statistics for MSVC x64 binaries: no source opened.
- Published static-recompiler approach for MSVC `__CxxFrameHandler3/4`, funclets, and `RtlUnwindEx`-style dispatch on arm64: none found. How Prism/ARM64EC/FEX unwind through translated frames: not covered by anything opened.
- TEB `gs:` handling, `rdtsc`, `cpuid`, `KUSER_SHARED_DATA`: no primary sources opened.
- x87 in x64 game code: Box64 and Rosetta clearly emulate it, but I have no source on how much x87 MSVC x64 games contain.
- Whether Titanfall 2 actually JITs or self-modifies: Squirrel VM implementation were not confirmed.
- Performance numbers for sse2neon/SIMDe on large engines.
- Official docs for the new macOS 27 cross-architecture entitlement.

## (4) Dynamic and hybrid fallbacks

### Takeaway
Within the pages I could open, Box64 does not run on macOS at all; FEX runs on macOS only through CodeWeavers' private port (shipping inside CrossOver, not as an embeddable library) or inside a Linux microVM; Rosetta works only for whole x86_64 processes and cannot be mixed into an arm64 process. The only demonstrated hybrid static-plus-dynamic design is Arancini's own runtime, which is a research system on Arm/RISC-V Linux. A JIT in a personal macOS build is allowed and does not need the App Store.

### Cited Findings
- **Rosetta**: whole-process only (no arm64/x86_64 mix), supports JIT-generating x86_64 apps, cannot translate kernel extensions or x86 VMs, AVX/AVX2 yes, AVX512 no. — [Apple docs](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment.md). So Rosetta cannot be embedded as a fallback inside a native arm64 recompiled binary.
- **Box64**: MIT; targets ARM64, RISC-V (RV64) and LoongArch **Linux**, not macOS or Windows; supports Wine64/Proton for Windows apps (32-bit parts need Box86); README says its DynaRec is 5-10x faster than its interpreter and mentions an EuroSys 2026 paper. — [github.com/ptitSeb/box64](https://github.com/ptitSeb/box64)
- **FEX-Emu**: JIT x86/x86-64 emulator for ARM64 Linux; per the FEX-2306 notes it asks for hardware TSO via prctl on Asahi. — [FEX-2306](https://newreleases.io/project/github/FEX-Emu/FEX/release/FEX-2306). A community Podman image runs FEX in a libkrun Linux microVM on Apple Silicon as a Rosetta/QEMU replacement, reports up to ~30x speedup for repeated runs from a JIT code cache (Python 3,371 ms to 111 ms; GCC 1,328 ms to 45 ms) and ~0.7 s cold-start overhead, with 13 of 17 known problem cases resolved. — [Podman discussion 28549](https://github.com/containers/podman/discussions/28549). FEX 2604 (April 2026) release news mentions avoiding JIT exits for x87 transcendentals (3.7x for some operations) **[UNVERIFIED: snippet]** — [Phoronix](https://phoronix.com/news/FEX-2604-Released)
- **CrossOver (CodeWeavers) native-ARM64 preview**: integrates a macOS port of FEX to run x86 Windows software without Rosetta; needs macOS 26.5+; no D3DMetal, some launchers fail, bottles not migratable at preview; Rosetta is scheduled to be largely discontinued in macOS 28. — [macmagazine](https://macmagazine.com.br/post/2026/07/31/crossover-27-ganha-versao-de-teste-com-suporte-a-chips-apple-silicon/), [ithinkdiff](https://www.ithinkdiff.com/?p=343215), [borncity](https://borncity.com/news/crossover-fuer-mac-arm64-version-ohne-rosetta-2-verfuegbar/). Whether the port is open source or reusable as a library: not stated in what I read.
- **Arancini** is the only system I found designed to mix both: its dynamic translator is the on-demand fallback for code the static pass could not resolve, sharing one IR. — [Arancini slides](https://dse.in.tum.de/wp-content/uploads/2026/03/Arancini-Asplos26-unrolled.pdf)
- **Windows Prism / Windows-on-Arm**: x64 emulation interoperates with Arm64EC code in one process. — [Microsoft Learn: Arm64EC](https://learn.microsoft.com/en-us/windows/arm/arm64ec). No 2025-2026 Prism game overhead figures found.
- **JIT on macOS for a personal build**: Apple states that an app that does not adopt the Hardened Runtime can use `MAP_JIT` without any entitlement (I did not test unsigned or ad-hoc-signed binaries; arm64 macOS code-signing requirements were not covered by the page); the `com.apple.security.cs.allow-jit` entitlement is only required when the hardened runtime is enabled; Apple silicon enforces W^X for everyone; write via `pthread_jit_write_protect_np` (or the allowlist callback API with `com.apple.security.cs.jit-write-allowlist`), then `sys_icache_invalidate`. — [Apple: Porting JIT compilers](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon.md)
- **QEMU / Unicorn as oracle**: rev.ng uses QEMU's TCG to lift code, and Risotto is a QEMU modification. — [docs.rev.ng](https://docs.rev.ng/what-is-revng/), [TU Delft](https://research.tudelft.nl/en/publications/risotto-a-dynamic-binary-translator-for-weak-memory-model-archite). No page about Unicorn or QEMU user-mode on macOS as a differential-testing oracle was opened.

### Inferences
- A hybrid design on macOS 27 means shipping your own interpreter or JIT inside the arm64 process (as Arancini does) rather than calling Rosetta. Candidates: FEX's core (if CodeWeavers' port or upstream permits), Box64 (needs porting to macOS: Linux syscalls, 4K vs 16K pages), or a purpose-built interpreter/small JIT for the residual indirect targets. Whether FEX's emulation core can be linked as a library, or Box64 embedded, was not verified from any source I opened.
- Since the final product is a personal build, JIT entitlement friction is low: no App Store and, with no hardened runtime, no `allow-jit` entitlement. The cost is design effort for W^X toggling and I-cache invalidation.
- Per-function differential testing is plausible with QEMU user-mode or Unicorn running the original x64 code against the recompiled function, but 16K-vs-4K pages, TEB/`gs:` and Windows ABI differences would need harnessing (no source; reasoning only).
- If an escape hatch is needed for a few unresolved regions, the cheapest correct option is probably a slow interpreter for those regions, not a full JIT (reasoning; Arancini's evidence is the opposite direction, on benchmarks where static coverage was incomplete).

### Gaps
- 2025-2026 overhead figures for Box64, FEX, Rosetta, Prism on games: none found with reliable method; only a 2022 Box86 comparison page appeared in search and was not opened.
- Whether FEX or Box64 can be embedded as a library for an unresolved-code fallback.
- Whether CodeWeavers' FEX-for-macOS is open source and what it does for TSO and 4K/16K page size.
- Unicorn and QEMU user-mode status and macOS suitability as an oracle.
- Prism / ARM64EC details for exceptions and indirect calls beyond the overview page.
