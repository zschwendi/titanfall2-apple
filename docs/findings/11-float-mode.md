# 11. SSE float semantics as plain C on arm64: FPCR default vs FPCR.AH

Date 2026-10-08. Code and raw output: `experiments/afp/` (`out/` is git-ignored; every number
below is regenerated by the commands at the end).

## Answer in five lines

1. With FPCR.AH set, plain C reproduces SSE bit for bit for add, sub, mul, div, sqrt (scalar and packed,
   single and double, all four rounding modes, every DAZ/FTZ combination), min/max written as a
   compare-select, `comis`/`ucomis` flags, `cmpXX` masks, int to float, float to float, and packed int to
   float. Without AH the same C differs only in NaN results, and cannot express DAZ and FTZ separately.
2. Float to int conversions (`cvt*2si`, `cvt*2dq`) need special C with or without AH: ARM saturates and
   turns NaN into 0, x86 returns INT_MIN for every invalid case. The range-checked form below is exact.
3. `rcp*` and `rsqrt*` match the emulator as `1.0f / x` and `1.0f / sqrtf(x)`, but the emulator computes an
   exact quotient and real x86 returns a table approximation. "Exact" for these means "equal to Unicorn",
   not "equal to a CPU".
4. Leaving AH on for a whole thread is not safe. It changes FNEG/FABS on NaN bit patterns, and clang builds
   the 64-bit mask `0x7fffffffffffffff` as `fneg(all-ones)`. Measured: `cbrt(-8.0)` returns +2, lifted-style
   `andpd` with a known mask stops clearing the sign, 10 of 152 libm/C/string rows differ for non-NaN input.
   Scope AH to lifted code.
5. Unicorn itself is wrong, relative to the Intel manual, in three places that matter here (FTZ ignored, NaN
   operand choice, rcp/rsqrt). The oracle was corrected for the first two; the third cannot be.

## Method

**Oracle.** The real x86 instruction (register form, `xmm0, xmm1` or `eax/rax`) runs in Unicorn 2.1.4 over a
whole input set in one `emu_start`, inside a small load/store loop (`afp_x86.py`; every encoding is
disassembled with Capstone at startup). Read back: `xmm0` and `rax` (for compares `RFLAGS & 0x8d5`, i.e. CF PF
AF ZF SF OF). The upper lanes of `xmm0` are filled with random bits and must come back unchanged, so
"scalar op writes lane 0 only" is checked, not assumed.

**Candidates.** `afp_lab.c`: 135 (operation, formulation) pairs over 90 operations, written the way the lifter would emit them
(`Xmm` union, scalar ops write lane 0, packed ops copy to locals and loop over lanes). Built with
`clang -O2 -ffp-contract=off`. A driver sets FPCR, runs one formulation over the same records, restores FPCR.

**Modes.** MXCSR RC maps to FPCR.RMode as 0 to 0, 1 (down) to 2, 2 (up) to 1, 3 to 3.
- *default*: RMode only, plus FZ when MXCSR has DAZ or FTZ (the best plain ARM can do).
- *AH*: AH, RMode, FIZ = DAZ, FZ = FTZ.
- Also run: AH+NEP (baseline config only; same bits as AH everywhere), and FIZ/FZ without AH (not exact: no NaN rules).
Configs per op: 4 RC x DAZ x FTZ where each applies (16 for add/sub/mul/div, `cvtsd2ss`, `cvtpd2ps`).

**Inputs, per op and config.** 100,000 uniform-random bit-pattern pairs; 60,000 structured-random pairs
(mutations of boundary values, equal and adjacent exponents, exact half-way cases, integers and halves,
NaNs of every payload, products and quotients landing within 3 ulp of 2^-126 or 2^-1022, doubles on both
sides of the binary32 range edges); the full cross product of a boundary set (162 binary32 values: both zeros,
both infinities, quiet and signalling NaNs with varied payloads, denormals, smallest and largest normals,
tie and near-integer values, 2^31, 2^32, 2^63, 2^64 and neighbours; 197 binary64 values; 66 and 108 integers).
Unary ops use the boundary values alone. Packed ops carry 2 or 4 test lanes per record, and the boundary
pairs slide through every lane position. 424 million lane comparisons in total, 2,175 result rows, 0 harness errors.

**Negative controls (must fail, and do):** `(int)v`, `fminf`, `fmin`, `fcvtns`, `frecpe`, `frsqrte`.

**Corrections to the oracle** (found by the harness; Unicorn is QEMU 5.0 softfloat):

- **FTZ ignored.** Unicorn does nothing for MXCSR.FTZ on SSE (`mulss 2^-126 * 0.5` returns 00400000 with FTZ=1).
  The SDM says tiny results flush to a signed zero when underflow is masked, tininess detected after rounding.
  Oracle: run the emulator with FTZ ignored, then flush every lane whose exact value rounds (unbounded exponent)
  below 2^emin, keeping the sign. Both sides of the window are exercised (summed over configs: 11,576 results
  the emulator rounded up to 2^emin that are flushed, 13,388 that are correctly kept).
- **NaN operand choice.** With two NaN operands, or SNaN+QNaN, Unicorn applies the x87 rule (QNaN wins, else
  larger significand): `addss(7f800001, 7fe27b08)` gives 7fe27b08. The SDM (table 4-7, SSE column) says the first
  source operand, quieted: 7fc00001. Oracle: result lane replaced by the quieted first NaN, else the quieted second.
- **rcp/rsqrt.** `rcpss`, `rsqrtss` return the exact quotient in Unicorn (`rcpss(1.0)` = 1.0); hardware uses a table
  with relative error up to 1.5 x 2^-12. This cannot be corrected; those rows mean "equal to the emulator".

Self-check of the emulator itself: add, sub, mul, div, sqrt, binary32 and binary64, all four RC, 1.08 million
finite non-zero results, against an exact `Fraction` model (`afp_model.py`): 0 differences.

## Is it safe to leave AH on for a whole thread? No

`afp_safety.c` runs 152 libm, C-expression, array-loop, bit-mask and string<->float rows once per FPCR setting on
24,000 inputs each (random bits, ranges, denormals, specials) and compares result bits with FPCR=0; builds at
-O0, -O2, -O3, -O3 -ffast-math, plus one with Accelerate. A difference is "REAL" if no input was a NaN and
neither result is a NaN.

- 142 of 152 rows are bit-identical for every non-NaN input at -O2, including `sqrtf`, about 50 single-precision
  libm functions, compiled float loops (sum, dot, max, min, clamp, a/b, casts), `snprintf %.9g`, `strtof`,
  `strtod`. The only differences in those rows involve NaN inputs or NaN results (sign of the default NaN).
- 10 rows change (9 at -O0): libm `cbrt` (`cbrt(-8.0)` = +2), `erf`, `erfc`, `tgamma`, `copysign`, `ldexp`
  (sign of zero), `nextafter` (wrong sign), `csqrt`, plus compiled `x & 0x7fffffffffffffff` on 64-bit lanes and
  compiled `copysign(double)`. With Accelerate: `vvrecf` (11,306 of 24,000 differ, by one ulp in the examples) and `vvsqrtf`
  (5,375; `vvsqrtf(0x007fffff)` returns +inf).
- Cause, measured for the compiled cases (`afp_negabs.c`): under AH, FNEG and FABS return a NaN input unchanged
  (`fneg(ffffffffffffffff)` = ffffffffffffffff, normally 7fffffffffffffff). clang materialises the 64-bit mask
  `0x7fffffffffffffff` as `movi.2d v, #-1; fneg.2d v, v`. A lifted `andpd xmm, [known mask]` compiled at -O2
  leaves lanes -1.5 and -2.5 unchanged under AH (`afp_traps.c`). Built with `-fno-vectorize -fno-slp-vectorize`
  the same code compiles to `and x8, x8, #0x7fff...` (assembly inspected, not run). The libm and Accelerate failures are assumed to
  have the same or a FRECPE/FRSQRTE cause; I could not disassemble them (lldb would not attach).
- NEP changes nothing in any row. clang 21 emitted an explicit `movi` for all 7 NEON patterns I tried where it
  could have relied on scalar ops zeroing upper lanes, so NEP=1 would probably be harmless, but it is not needed.
- FIZ+FZ changes 93 rows, as it should (denormals flush). That is a property of the game's MXCSR, not of AH.

Consequences: set AH when entering lifted code and clear it before any call into libm, Accelerate, Metal or other
host code (a write pair costs 17.6 ns, measured, 8.8 ns each). A new `pthread` starts with FPCR=0; a signal
handler runs with the interrupted thread's FPCR. Lifted code itself needs the mask hazard handled: no NEON
auto-vectorisation of integer ops on 64-bit lanes, or a scan of the generated assembly for `fneg` after
`movi ... #0xffffffffffffffff`.

## Traps

1. **Default NaN sign and NaN choice.** Plain ARM gives 7fc00000 for invalid operations and prefers a signalling
   NaN; x86 gives ffc00000 and the first operand. AH fixes both.
2. **AH has side effects on FNEG/FABS/FRECPE/FRSQRTE** (previous section). Not a free global switch.
3. **FPCR is per thread**, not inherited by new threads, inherited by signal handlers, and costs about 9 ns a write.
4. **The compiler may reorder commutative operands.** clang turned `*p + x` into `x + *p`: with two NaN operands
   `*p + x` returned x's NaN (x86: the first operand's). With `restrict` it merged `a+b` and `b+a`
   (7fc00001 for both; x86 gives 7fc00001 and 7fc00002). Inline-asm `fadd`/`fmul` keeps operand order and was
   exact in every config (variants `*__asm`). Only visible when both operands are NaN.
5. **Contraction.** clang's default `-ffp-contract=on` fuses `a*b+c` inside one C expression into `fmadd`: 55,379
   of 100,000 random triples differ from mulss then addss. Build lifted code with `-ffp-contract=off`.
6. **Constant folding** uses +NaN: `INFINITY - INFINITY` folded to 7fc00000 while the same operation at run time
   under AH gives ffc00000 (x86). Anything the compiler can fold at build time loses the NaN sign.
7. **Float to int is undefined in C and differs on ARM** (traps above, table). `(int)v` for NaN or out of range is UB
   and clang is free to exploit it. Use the range test.
8. **Round before the range test** for `cvtss2si`/`cvtsd2si`: `rint(2147483647.5)` is 2147483648.
9. **`fmin`/`fminf` from libm are minNum**, not x86 min. NEON `fmin` matches x86 only under AH and only for DAZ=0.
10. **DAZ and FTZ are independent on x86; FZ alone is not.** Without AH, FZ flushes inputs too and detects tininess
    before rounding: `mulss 1b6a9cc0 * 248bab31` (0.99999998 x 2^-126) gives 00800000 in the SDM model and with
    AH+FZ, but 00000000 with FZ alone. FIZ alone is a correct DAZ.
11. **MXCSR status flags and unmasked exceptions are not modelled.** Plain C sets none of IE DE ZE OE UE PE
    (FPSR has IOC IDC DZC OFC UFC IXC); `stmxcsr` appears 43 times in the game. Untested: whether an FPSR to
    MXCSR mapping is faithful under AH. Apple silicon cannot trap on FP exceptions.
12. Not tested: memory-operand forms, SSE3/SSE4 float ops (`addsubps` occurs 12 times in the game although the CPUID
    shim reports SSE2 only), AVX, x87. (`addsubps` and `haddps` were measured later: addendum 4.)

## Unverified against real hardware (matches the emulator or the SDM only)

- H1 `rcp*` and `rsqrt*`: the emulator returns the exact quotient. Hardware returns an approximation; it differs
  between vendors, and from memory (not checked) Intel returns 0x3f7ff000 for `rcpps(1.0f)`. The M3's AH
  `frecpe(1.0)` is also 3f7ff000, and its error bound is inside Intel's, which suggests it is the better
  stand-in, but nothing here shows it bit-equal to any CPU. Differential tests against Unicorn will bless the
  wrong answer for these instructions (census: `rcpps` 126, `rsqrtps` 126, `rsqrtss` 69).
- H2 FTZ and the tininess rule: Unicorn ignores FTZ; the oracle is a model of the manual. AH+FZ agreed with it
  in all 16 configs including the window cases, which supports the model but is not hardware.
- H3 NaN operand choice: SDM table 4-7, not measured on a CPU. Unicorn disagrees with it; ARM AH agrees with it.
- H4 min/max with DAZ=1 and a denormal operand selected: does hardware return the original denormal (the
  emulator, and the compare-select form) or a flushed zero (the NEON `fmin` form)? Unknown.
- H5 DAZ on compares and conversions, and cvt rounding of denormals, are the emulator's behaviour.

`afp_hw_probe.c` is a 50-line program that checks H1 to H4 on a real x86-64 CPU. It compiles for x86_64 but was
not run: this Mac has no Rosetta and the study did not cover other machines.

width (zeros, denormals, smallest normals, 1, 2, infinities, quiet and signalling NaNs of both

**H5.** DAZ on compares and conversions: the emulator against the CPU on `comiss ucomiss comisd

the low 11 bits zero, all ones or mixed, the scalar instruction under the default MXCSR (16,384
cases) and the packed one, the four exponents in its four lanes, under each of the six other
settings of the float test (24,576 cases): 114,688 lanes. Then 820 special operands (both
zeros, both infinities, quiet and signalling NaNs with payloads, denormals, the smallest and
largest normals, 512 random bit patterns) scalar and packed under all seven settings (7,658
cases, 13,412 lanes).

| Class of operand (lanes per operation) | `rcp` | `rsqrt` | Differs |
|---|---|---|---|
| table, 4 exponents (114,688) | 12 bits of result, low 11 bits of the mantissa zero | the same | 0 |
| zero (42) | infinity of its sign | infinity of its sign | 0 |
| infinity (28) | zero of its sign | +inf: +0; -inf: ffc00000 | 0 |
| NaN, quiet 252 and signalling 273 | the operand, quieted | the operand, quieted | 0 |
| denormal (469) | infinity of its sign, **with or without DAZ** | infinity of its sign, the negative ones too | 0 |
| negative normal (6,020) | a normal result of the operand's sign, or a zero as below | ffc00000, the default NaN | 0 |
| positive normal (6,328) | a normal result; a **zero** of the operand's sign where it would be denormal (magnitude of 2^126 or more: 1,106 lanes of both signs) | a normal result | 0 |

No result of any of the 820 special operands depends on the MXCSR setting (rounding mode, DAZ,
FTZ), and the CPU changed MXCSR in none of the 97,236 cases. Control: the exact quotient, which
is what the emulator computes, equals the CPU's result in 44 of 121,016 `rcp` lanes and 53 of
121,016 `rsqrt` lanes with a positive normal operand.

**No class needs a correction**, so the helpers are the bare instruction. This is Intel's table.
AMD's processors return other bits for the same operands (not measured here: there is no AMD
machine); a game that ran on AMD saw those.

**The harness** no longer lets the emulator judge these four (`harness/oraclefix.py`,
`HARDWARE_ONLY`): the expected side of an instruction case is the CPU or nothing, under the
default MXCSR too, and a function-test case that reaches one is inconclusive. A translation
that returns the exact quotient fails all four mnemonics in the self-tests.

## Addendum 4: addsubps and haddps measured (2026-10-10)

Trap 12 left the SSE3 float instructions untested, and the emulator is wrong for these two under
FTZ and where both inputs of a lane are NaNs, so nothing could say how to write them.
`harness/hadd_sweep.py` asked the real CPU (Core i5-7600K, `tools/hworacle`, cache family
`hadd-sweep`): `addsubps xmm1, xmm2` and `haddps xmm1, xmm2`, 194 cases each under each of the
seven MXCSR settings of the float tests, 2,716 cases, all answered. A case holds four lane pairs;
188 pairs slide through the four result lanes, so each pair is computed in every lane.

Measured from the CPU's answers alone, the same under all seven settings:

| Question | `addsubps` | `haddps` |
|---|---|---|
| Which lanes (6 cases per setting with eight different exact integers; one formula fits each lane) | `r = {d0 - s0, d1 + s1, d2 - s2, d3 + s3}` | `r = {d0 + d1, d2 + d3, s0 + s1, s2 + s3}` |
| Both inputs of a lane NaNs (every ordered pair of 8 NaNs, 4 quiet and 4 signalling, both signs, so each pair in both orders: 224 lanes per setting; and 24 lanes of the instruction test's generator) | the destination's lane, quieted: 248 of 248 | the **lower** lane of the two (`d0` of `d0 + d1`, `s2` of `s2 + s3`), quieted: 248 of 248 |
| One input a NaN, the other a number, an infinity, a zero or a denormal (144 lanes per setting) | that NaN, quieted, sign kept, in the subtracted lanes too: 144 of 144 | the same: 144 of 144 |
| Invalid: the sum or difference of two infinities that has no value (8 lanes per setting) | ffc00000: 8 of 8 | ffc00000: 8 of 8 |

The Intel manual writes the horizontal sum as `SRC1[63:32] + SRC1[31:0]`, upper lane first. On
the CPU the lower lane is the first operand in the sense of the NaN rule (SDM vol. 1 table 4-7).
The manual's order says nothing about NaN payloads, so this is a measurement, not a disagreement
with it; the question is settled by it.

Then the formulation of the table row, lifted by family `sse_hadd` and run by the test driver in
the guest float mode, against the same answers: 2,716 of 2,716 cases agree in every bit of the
state, 10,864 result lanes. Besides the pairs above: 12 pairs with infinities, 12 with signed
zeros and exact cancellation (the sign of a zero sum under round-down), 18 with denormal inputs
or results (DAZ, and FTZ's flush of a tiny result), 18 rounding ties and overflows, and 40 pairs
of the instruction test's own generator. `addpd`-width forms (`addsubpd`, `haddpd`, `hsubps`,
`hsubpd`) were not measured: no family translates them.

Re-run from the cache: `.venv/bin/python harness/hadd_sweep.py --offline` (it ends `HADD-SWEEP
AGREES`).

**The emulator is not corrected for these two.** The instruction test takes their expected
result from the CPU. The function test still judges a function that contains one by the
emulator as it is: wrong only where both inputs of a lane are NaNs, and under FTZ, which the
function test does not set (`harness/oraclefix.py`: `NAN_FIRST_OPERAND` and `FTZ_ARITH` are the
sixteen `add/sub/mul/div` mnemonics). An instruction case under the default MXCSR that the CPU
has not answered falls back on the same uncorrected emulator.
