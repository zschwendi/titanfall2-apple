# 15. x87, MMX and 3DNow! instructions: real code or mis-decoded data

Scope: the unwind-table (.pdata) ranges of the 24 game images (`game/bin/x64_retail/*.dll` except `d3dcompiler_46.dll`, and `game/server.dll`): 7,604,396 instructions swept. Static analysis only; nothing was run and `Titanfall2.exe` was not read. The scanner is `tools/scout/x87_scan.py`; `.venv/bin/python tools/scout/x87_scan.py game --functions` reproduces every number here.

## Summary

1. 363 sites in 149 functions: 324 x87, 29 `wait`/`fwait` prefixes, 7 MMX and 3 3DNow! instructions.
2. Real: 14 x87 instructions (7 `fnclex`, 7 `fldcw`) in 7 functions, two in each of client, engine, server, vgui2, vguimatsurface, vphysics and vstdlib: one routine of 236 bytes with the same mnemonic sequence in seven images.
3. The real code never pushes onto the x87 stack (depth 0 at every reached instruction), and no MMX or 3DNow! instruction is reached.
4. Data: 287 sites in 117 functions; 285 of those sites lie inside 115 jump tables that a dispatch in the same function reads, so the tables sit inside unwind ranges; 2 functions are data on weaker evidence.
5. Undetermined: 62 sites in 25 functions; 42 sit behind dispatches the descent cannot follow, and 20 sit in functions whose complete descent from a referenced entry never reaches them.
6. For the real code the translator needs `fnclex`, `fldcw` and one per-thread control-word slot, and no register stack; `fldcw` loads its value from memory, so precision, rounding and exception-mask bits are not known statically.
7. The 62 undetermined sites are the open question: if any is real x87 arithmetic the translator needs a stack, and for those sites the answer is undetermined.
8. The census count of about 300 is 324 x87 here; the waits, MMX and 3DNow! instructions are counted separately.

## Method

**Sites.** Every `.pdata` range is swept with Capstone 5, the census method: a decode failure advances one byte. A site is an instruction in Capstone's FPU, MMX or 3DNOW group, or with mnemonic `emms`, `femms`, `fxsave`, `fxrstor`, `fninit`, `wait` or `fwait`. A function is its primary `.pdata` entry; split fragments join their parent through `cpu_core.function_table`.

**Reach.** Recursive descent (`cpu_core.descend`) starts at the entry only. It follows direct branches, both sides of conditional branches, and resolved switch dispatches. It stops at `ret`, at unconditional jumps, and at indirect jumps it cannot resolve; the count of those is reported, so reach is a lower bound when it is nonzero. A fragment is entered only by a real branch or fall-through. Seeding every `.pdata` start was tried and rejected: it counted fragments that nothing branches to, which decode as data.

**Repairs to the shared decoder.** Made in `x87_scan.py` by replacing functions in `cpu_core` at import time, without editing `cpu_core`:

- `resolve_switch_general` replaces `cpu_core.resolve_switch`. The shared version takes the table base from the `lea` target and ignores the displacement on the dispatch load, so it reads RVA 0 when the `lea` yields 0. It also cannot handle the two-level byte-map form. The replacement adds the displacement, follows register copies when looking for the bound, and handles the byte-map form. Across the 24 images it resolves 297 dispatch tables: 281 have every entry inside their function, and 16 have one entry outside.
- Prefixed mnemonics are reduced to the instruction (`repz ret` becomes `ret`, `notrack jmp` becomes `jmp`). The shared version tests mnemonics with `startswith`, so it ran past `repz ret` into the bytes after it. One function was reached only that way, and its `fcmovu` is no longer counted as real.

**Evidence and classes.** A site is *reached* if descent from the entry reaches it, and *in a jump table* if it lies inside a table that a dispatch reached by descent reads. A table is used as data evidence only when every one of its entries lands inside the function. The 16 partial tables still supply their in-range targets to descent, but their bytes are not called data; four sites lie in them (three x87, one `wait`) and are undetermined. Branch targets are not evidence, since a direct branch can be decoded from data just as easily. A function's entry counts as *referenced* if another function branches to it, a RIP-relative operand names it, a base relocation stores it, or it is exported.

- **real**: a reached site that is not a bare `wait`, a referenced entry, and no x87 depth conflict on the reached instructions.
- **data**: every site lies in a jump table read by a reached dispatch (basis "jump table"); or every site lies within 24 bytes of undecodable bytes and nothing refers to the entry ("undecodable"); or a complete descent from an unreferenced entry reaches no site ("unreached").
- **undetermined**: everything else, with the basis stated in the table.

The x87 stack depth is computed over the reached instructions: pushes add one, pops and arithmetic-pops subtract one. A pop at depth 0 is counted as an underflow, which means the routine takes a value from its caller's `st(0)`. No real function has an underflow.

**Checks.** Every resolved table was checked to see whether its entries land inside the function. 281 of 297 do; the other 16 are the partial tables above. Sampling the unresolved dispatches before the repair showed three causes: the `lea` that sets the base lay outside the search window, and the bound was compared on a register that a `movsxd` had copied from. The repair covers those three. Fourteen functions still have a dispatch the resolver does not follow, and their shape was not characterised further.

## The real routine

Seven copies, one per image: client `0x80ad70`, engine `0x5237b0`, server `0x7e5b50`, vgui2 `0x0cfe40`,
vguimatsurface `0x1c20f0`, vphysics `0x1509a0`, vstdlib `0x030260`. Each spans 236 bytes of unwind range and
has the same instruction sequence, compared by mnemonic. Descent from the entry reaches 48 instructions and
no `ret`. The sequence, in order, is:

- `ldmxcsr dword ptr [rcx+0x58]`, then `fnclex`, then `fldcw word ptr [rcx+0x5c]`;
- ten 16-byte loads of xmm6 to xmm15 from `[rcx+0x60]` upward;
- general-purpose registers loaded from `[rcx+0x40]` onwards;
- `mov rdx, [rcx+0x50]`, then one call to an address outside the range, then a direct `jmp` to `0x80ae13`
  (client copy), past which the descent meets one indirect `jmp rdx` at `0x80ae11` that it cannot resolve.

Reading: the routine restores MXCSR, the x87 control word, XMM6 to XMM15 and callee-saved registers from a
structure at `rcx`, and appears to leave through an address loaded from that structure. That is the shape of a
setjmp or longjmp, or a coroutine or fiber resume. The identity is not confirmed. Each copy is branched to
from 2 to 16 places in its own image (`calls` column), so it is a shared routine rather than a dead copy.

The x87 use is self-contained: `fnclex` clears the exception flags and `fldcw` loads a control word. The stack
depth is 0 throughout, and there is no underflow. The value loaded by `fldcw` comes from memory, so its
precision, rounding and exception-mask bits are not determined by this code.

## What the translator needs

For every instruction the scan reaches: `fnclex` and `fldcw`, a per-thread 16-bit control-word slot that
`fldcw` writes, and no x87 register stack. Real code never reads the control word back (no `fnstcw` is reached).
The control-word value would matter only if x87 arithmetic were found in the undetermined code, and none has
been found in reached code.

## What could not be determined

- The 62 undetermined sites in 25 functions, which are the only open question. 42 sit behind dispatches the
  descent cannot follow, after the repaired resolver. 20 sit in 11 functions whose complete descent from a
  referenced entry does not reach them; these may be real code entered at a point other than the entry, data,
  or code reached through a resolver gap. None of these 62 is settled.
- Which of the 14 unresolved dispatches' shapes remain, beyond the three causes repaired.
- The two weaker data verdicts (one unreached site in engine `0x3a8720`; one site in localize `0x26700`,
  inside undecodable bytes with nothing referring to the entry).
- The value and bit layout of the control word, and which code writes the structure at `[rcx+0x5c]`. Those
  writers are outside this survey's remit and are not located in these images.
- The identity of the context routine.
- Anything outside the unwind ranges, which this scan does not sweep, and `d3dcompiler_46.dll`, excluded by
  the brief.
- Dynamic behaviour: no run was made, so which of the seven copies executes, and how often, is not known. The
  real classification is static reachability from the entry.
