# Faults and limits of DXMT that this project has met

Started 12 October 2026. A running list: add an entry when a new one is met.

**Nothing in this file is sent to anyone.** DXMT's maintainer accepts no contribution written or co-written by
an AI (fork `CONTRIBUTING.md:25-29`), and the project's rule is "note and move on": each
fault is written down here and worked around in our fork or on our side of the seam. No issue, no pull
request, no patch, no text of ours goes to DXMT's maintainer or to any other place.

**How to read it.** Paths are relative to `third_party/dxmt`, branch `tf2` at `b8d3fe2` (upstream `e94c312`
plus the project's five patches, `patches/dxmt/`). Lines are the fork's at that commit. "Fault" means DXMT
does something wrong or dangerous; "limit" means DXMT lacks something, on purpose or not yet; "native" means
it shows only in the build without Wine, which upstream calls experimental. Where an entry comes from:
**[F35b]** `docs/findings/35-dxmt-build.md`, **[F35w]** `35-dxmt-window.md`, **[F35n]** `35-dxmt-native.md`,
**[research §n]** `docs/research/dxmt-architecture.md`.
"Read" means the lines were read in
this study; "ran" means a program of ours showed it.

## C. Native build: things Wine used to provide

| # | What | Where in the fork | Kind | What we do |
|---|---|---|---|---|

So: the log file is `<DXMT_LOG_PATH>/_dxgi.log` (or `./_dxgi.log`), the default shader cache directory is `dxmt//` under the user's cache directory, shared by every native program, and `[exe name]` sections of `dxmt.conf` can never match. [F35b §6] | `src/util/util_env.cpp:78-96`; `src/util/log/log.cpp:109-126`; `src/dxmt/dxmt_shader_cache.cpp:22-33` | fault (native) | The host sets `DXMT_SHADER_CACHE_PATH` and `DXMT_LOG_PATH` (or `none`) before loading; settings go through `DXMT_CONFIG`. ## Not faults of DXMT (so that nobody files them)

- A null feature-level list gives 11_0: that is Direct3D's own default list [from memory of Microsoft's documentation of `D3D11CreateDevice`; not checked against the page in this study].
- The display list being empty while the display sleeps was a mistake of our patch 2's first version, fixed there (F35w §2).
- `SDL_Metal_CreateView` rewriting `drawableSize` is SDL's behaviour (F35w §7.3).
